## 1. 四层总览

```
┌─ L3  core/authoring/  ── 视图服务：文档、命令总线、布局、端口 UI
├─ L2  core/runtime/    ── 运行身份、记录、数据集、导出
├─ L1  core/graph/      ── IR、图结构、求值、缓存、调度、内核契约
└─ L0  core/            ── 契约与机制：量纲、ABI、端口、插件、诊断（地基）
     ─────────────────────────────────────────────────────────────
        views/       ⊂ L3 消费者：Qt 界面（节点编辑器 / 表格 / 仪器面板）
        plugins/     ⊄ 任意层：内容（模型、仪器、内核实现、视图项、实验）
        tests/ bench/     贯穿全部层
```

**核心断言：`views/` 与 `plugins/` 可以整个删掉，`core/` 仍能编译并通过全部测试。**
这是 CI 必须验证的一条（见 `enforcement.md` §6）。

## 2. L0 —— 地基（`core/`）

L0 是本项目唯一不可插件化的部分，也是接口面必须最小的部分。

### 2.1 `core/units/` —— 量纲与量

| 项 | 内容 |
|---|---|
| 职责 | 编译期量纲推导；`unit` 字符串从类型自动生成 |
| 关键类型 | `Dim`, `Quantity<D>`, `Unit`, `Dimensionless` |
| 冻结 | `Dim` 的**底层表示**冻结（7 个指数）；API 可扩 |
| 依赖 | 无（最底层） |
| 为什么在地基 | 跨插件语义一致性的前提；所有 YAML/脚本都依赖它（冻结代价极高） |
| 不做 | 单位换算表、英制、量纲分析 UI —— 插件 |

### 2.2 `core/abi/` —— 跨边界内存布局

| 项 | 内容 |
|---|---|
| 职责 | 定义跨 Qt / 跨进程语言 / 未来 Web 共用的二进制布局与版本协商 |
| 关键类型 | `FieldBuffer`, `LatticeDesc`, `FieldDim`, `Version`, `abi_version` |
| 冻结 | **全部冻结**。改布局必须升 `abi_version` + 改 `static_assert` |
| 依赖 | **无**（连 `units` 都不依赖：量纲由自己的 `FieldDim` 承载，`abi.dim_matches_units_dim` 守这条一致性） |
| 为什么在地基 | 唯一共用物；改了所有消费者全废 |
| 不做 | 序列化格式、共享内存、socket —— 全是传输适配器插件 |

> **本行曾列出 `RuntimePlan` 与 `ParticleSoA`，两者在全仓库代码里出现 0 次。** 那是计划阶段的
> 名字，实现时被拆成了现在这套：`LatticeDesc` 描述「一段被描述的采样」（这才是批算子真正需要的东西，
> 而 `ParticleSoA` 会把一种数据布局烧进 ABI），而「怎么跑一次仿真」是 `graph/execution` 的
> `GraphRun` 与 `graph/kernels` 的 `IBatchAdvancer`——那是行为，不是内存布局，放进 ABI 会给每条
> 语言绑定一份需要跟着改的执行语义。文档跟着代码改，而不是反过来；这一行留在这里是因为「计划里的
> 名字后来没有了」本身是该被记下来的一件事，否则下一个人会去找一个不存在的类型。

### 2.3 `core/ports/` —— 端口类型注册表

| 项 | 内容 |
|---|---|
| 职责 | 类型的注册、校验、兼容性判定；量纲/单位校验的挂载点 |
| 关键类型 | `PortTypeId`, `PortTypeDesc`, `PortTypeRegistry`, `Value`, `TypeCheck` |
| 冻结 | 注册 API 冻结；**已注册类型的集合可扩**（加类型不算破坏兼容） |
| 依赖 | `units`, `diag` |
| 为什么在地基 | 新类型必须能被声明，否则新域无法接入（"加一个域零核心改动"的前提） |
| 不做 | UI 控件 —— 见 `authoring/portui/` |

### 2.4 `core/plugin/` —— 插件契约与加载

| 项 | 内容 |
|---|---|
| 职责 | 清单解析、兼容性判定、加载、失败降级、能力声明 |
| 关键类型 | `Manifest`, `Capability`, `PluginHost`, `CompatPolicy`, `PluginHandle` |
| 冻结 | 清单 schema + 兼容策略冻结 |
| 依赖 | `ports`, `diag`, `reflect` |
| 为什么在地基 | 加载契约；版本静默错配是插件架构最常见的失败模式 |
| 不做 | 具体插件；网络分发；GUI 插件市场 |

### 2.5 `core/diag/` —— 诊断与错误

| 项 | 内容 |
|---|---|
| 职责 | 结构化诊断、错误传播、日志、用户可见归因 |
| 关键类型 | `Diagnostic`, `Severity`, `Result<T>`, `ErrorCode`, `Sink` |
| 冻结 | `Result<T>` 与错误码分类 |
| 依赖 | 无 |
| 为什么在地基 | 插件出错必须能被用户看见并归因，否则平台不可用 |
| 不做 | 日志文件轮转策略、上传、遥测 |

### 2.6 `core/reflect/` —— 类型枚举与名字

| 项 | 内容 |
|---|---|
| 职责 | 类型 → 字符串（含单位、端口类型名）的唯一来源 |
| 关键类型 | `type_name<T>()`, `unit_symbol<D>()`, `enum_names<E>()` |
| 依赖 | `units` |
| 为什么在地基 | C++ / YAML / 脚本必须共用**同一份**名字来源，否则三处会漂移 |

### 2.7 `core/host/` —— 插件宿主（组合根）

| 项 | 内容 |
|---|---|
| 职责 | 把插件**装进**注册表：扫目录、映射动态库、按 manifest 协商能力、记录贡献、可撤销地卸载 |
| 关键类型 | `IPluginHost`（插件看到的全部表面，即插件 ABI）、`PluginHost`（应用看到的那一半）、`PluginOutcome` / `LoadReport` |
| 依赖 | `plugin`、`capability`、`ir`、`kernels`、`instrument`、`io`、`file` |
| 为什么必须存在 | `plugin` 只做「判断一份 manifest 值」，它自己的头文件写明**不**决定插件贡献什么；不写这一层，就从来没有任何代码调用过 `load_plugins` |

**它不是一个层，而是地基的边。** 其余每个模块都被写成「不知道邻居是谁」：`plugin` 判断 manifest 却不知道
插件贡献什么，`ir` 拥有描述符却不知道谁填充目录，`io` 拥有格式注册表却不知道谁注册格式。总得有人知道全部，
而在此之前那个「人」是应用本身——靠把内容静态链进去。那对一个「内容是库」的平台不是答案。

**为什么 ledger 不是多余的一层记账。** 注册表持有的是**非拥有**指针，指向插件自己拥有的对象，所以卸载
必须在动态库被释放**之前**把表清空。插件自己的 `unregister` 该做这件事，但它不够：`LoadedPlugin::unload`
无论 `unregister` 有没有清干净都会释放映射，于是漏掉一个节点类型的插件会留下悬空描述符，失败点离卸载点
任意远。所以宿主不信回调的完备性——每个 `add_*` 都记一笔，`unload` 自己按记录撤除。记录同时回答了别处
问不出的问题：**这是哪个插件贡献的**（`origin_of`）。`NodeDesc::source` 答不了，那是插件自己填的字符串，
它可以填错。夹具 `content.cpp` 的 `unregister` **故意是空的**，就是为了让这条记录可测。

**门禁在这里是什么、不是什么。** manifest 声明的是能力**位**，宿主在 `register_into` 之前比对授权。那是
声明检查，不是沙箱：接口是一个对象而不是按能力切分的门面，声明了 `kernels` 的插件照样能调 `add_node_type`。
明写出来，是因为不写就会有读者以为存在实际隔离——进程内插件是可信代码，这道门是为了抓**错误**（manifest
与代码不一致），不是为了关住恶意库。

**string 键的细粒度能力在宿主里被组合起来，而不是闲置。** `authoring/capability` 的 `ICapabilityProvider`
需要插件提供一个虚接口，而 `PluginExports` 只带位和回调——所以细粒度能力**目前无法由动态插件提供**。
宿主改为**自己合成** provider：offers 是声明位的名字，`needs` 就是那份声明，授权方是宿主。这消掉了
「插件对自己的描述决定了自己的权限」这个缺口，也把「动态插件拿不到细粒度能力」这件事记在这里而不是掩盖。
代价是：两个插件声明同一位就**互斥**（`Registry` 一个 id 只收一个 provider），
`needy` 夹具因此声明 `view_items` 而不是与 `content` 相同的位——这条约束对插件作者是真的，写在这里而不是
等他们自己撞上。

**测试用真库。** `tests/fixtures/host_plugin/` 五个夹具（content / refuses / hungry / empty / needy），
每个只偏离一处：注册内容、自带理由拒绝、声明未授权能力、声明空能力、依赖另一个插件。与 loader 的夹具
**故意不同**——那些不链宿主，才能就 ABI 与宿主产生分歧；这些必须链宿主，因为 `NodeDesc` / `KernelDesc` /
`IExporter` 本来就是宿主侧 C++。

## 3. L1 —— 图与执行（`core/graph/`）

### 3.1 `core/graph/ir/` —— 中间表示

| 项 | 内容 |
|---|---|
| 职责 | 节点/端口/边的**契约**，不含求值逻辑 |
| 关键类型 | `NodeId`, `PortId`, `PortRef`, `NodeDesc`, `PortDesc`, `Edge`, `NodeKind` |
| 关键决策 | `Node` 只允许**三个可选钩子**（`compute` / `validate` / `on_param`），是上限不是起点 |
| 关键决策 | `Param` 与 `Port` **统一**——端口带 `connectable` 标志，不设第二套机制 |
| 冻结 | 是（这是插件 API 本身） |

### 3.9 `core/graph/execution/` —— 运行循环与仿真模型契约

| 项 | 内容 |
|---|---|
| 职责 | 把一个节点驱动成一个算子、按步推进、记录成迹；以及**声明一个模型是什么** |
| 关键类型 | `IStateOperator`, `SimModelDesc`, `StateView`, `IOperatorBinder`, `GraphRun`, `check_run` |
| 关键决策 | 循环**刻意不依赖 `kernels`**：这里的算子只有两个方法，绑到 `IBatchAdvancer` 上会得到一个只能驱动批算子的循环；适配器属于插件，紧挨着它适配的代码 |
| 关键决策 | 第一个采样在第一步**之前**，所以 `n` 步的迹有 `n+1` 个采样；失败的步**保留已采样的部分** |
| 依赖 | `ir`, `structure`, `run`, `store`, `trace`, `validate`, `plugin`（C4 故障屏障） |

**`ISimModel` 这个名字没有被用来造一个同名的东西。** 章程 C6 要求 `IInstrument` 与 `ISimModel`
同时立项，而「推进状态的模型」在本仓库里已经以 `IStateOperator`（运行循环驱动的那一个）与
`kernels::IBatchAdvancer`（原生算子）的具体形式存在。再造一个同名接口去满足一个名词，只会得到两个
「模型」概念。补的是真正缺的那一半：**模型必须说清自己是什么**——`IStateOperator::describe()`
返回 `SimModelDesc`，四个字段，每一条都是**可证伪**的断言而不是注释：

| 字段 | 断言 | 谁去证伪 |
|---|---|---|
| `is_pure` | 同输入同输出，迹可重放 | `execution.model.a_pure_step_is_replayable`（逐位比较） |
| `time_reversible` + `round_trip_tolerance` | 一步 `+dt` 接一步 `-dt` 回到起点 | `execution.model.a_time_reversible_operator_round_trips`（真的跑一次往返） |
| `is_dimensionally_consistent` | 算术遵守节点声明的单位 | `execution.model.a_dimensionally_wrong_step_leaves_the_bound`（守恒量） |
| `is_independent_of_other_instances` | 两个实例/两次运行互不干扰 | `execution.model.interleaved_instances_do_not_disturb_each_other`（交错推进后逐位比较） |

**四个默认值都是怯懦的答案**（全 `false`）。什么都没声明的实现就是什么都没声明，据它生成的报告
不能比这更乐观；乐观的默认值会把「可复现」「物理自洽」印在一次其算子从未如此声称的运行上。

**`describe()` 是纯虚、没有默认实现**——一个默认实现就是一条没有人做过的声明。

**往返（round trip）不是「反解 ODE」。** 后者要解方程，前者只要把同一个规则用相反的符号再走一遍，
所以它正好落在运行循环自己的协议里：不需要第二套系统，也不需要参考解。这也是为什么算子的 `dt`
约定从「必须为正」放宽为「非零且有限，**负数合法**」：一个无法被证伪的声明就是注释。
`GraphRun::run` 仍然只走正向（`dt > 0`）——迹是时间序列，它的采样时刻必须非降——**宽的那一侧在算子、
窄的那一侧在运行**，两处都写明了理由。

**这一条是量出来的，不是想出来的，而且第一版是错的。** 直觉答案是「RK4 不是辛格式，所以不可逆」，
于是第一版把 `is_time_reversible()` 声明为 `false`，并附上一份「往返误差随时间增长」的测量——
那份测量读的是**状态自身的量级**而不是误差。逐值打印之后真相相反：RK4 在简谐振子上
`x0=1, v0=0, omega=2` 的一步往返相对误差约 `8.9e-13`（`dt=1e-2`）、一百步约 `8.9e-11`，
**随步数累积但源自舍入而不是截断**，所以答案是**是**。非辛与不可逆是两件不同的事，RK4 只占第一件。
现在这个声明由 `plugin.mechanics.oscillator_round_trips_to_its_start` 真的跑往返来检查。

**`kernels::IBatchAdvancer::is_time_reversible()` 有默认实现（`false`）**，与 `describe()` 的纯虚
不同：新增一个虚函数会让已有的每个内核都编不过，而「这个格式可逆吗」有一个安全答案。
`BatchOperator::describe()` 把内核的能力集映射成运行循环的四个字段，其中两个是**推导**的：
`is_pure` 就是「不消耗 RNG」，`time_reversible` 来自内核自己的声明；另外两个是适配器自己的性质，
而 `is_dimensionally_consistent` 保守地留 `false`——适配器不知道内核的算术是否守单位，
`IBatchAdvancer` 也没地方说，替内核断言物理正是这一层最不该做的事。

## 4. L2 —— 运行与数据（`core/runtime/`）

> **这一层是上一轮分析中发现"缺失"的部分。** 旧工程的抽象里只有"图 + 版本号 + 槽位"，
> 没有"一次实验运行"这个概念。没有它，整条可追溯链无处安放。

### 4.1 `core/runtime/run/` —— 运行身份

| 项 | 内容 |
|---|---|
| 职责 | 定义"一次运行"：seed + 参数集 + 图版本 + 插件版本快照 |
| 关键类型 | `RunId`, `RunSpec`, `RunRecord`, `Provenance` |
| 为什么在地基 | 章程 R2（同 seed 复现）与 C1（确定性重放）全挂在这里；否则每个插件各自发明一套 |
| 关键决策 | seed 属于**运行**，不属于插件私有状态 |
| 依赖 | `diag` |

### 4.2 `core/runtime/store/` —— 数据与拟合

| 项 | 内容 |
|---|---|
| 职责 | **结构**：测量值 = 值 + 不确定度 + 时间戳 + 有效标志；拟合结果 = 系数 + 协方差 + 残差 + R² |
| 关键类型 | `Dataset`, `Measurement`, `FitResult`, `Uncertainty` |
| 关键决策 | 契约在地基，**算法是插件**（回归 / 传播 / 卡方都是内容） |
| 依赖 | `units`, `ports` |
| 不做 | 任何具体的拟合或不确定度传播算法 —— 插件 |

### 4.3 `core/runtime/trace/` —— 记录

| 项 | 内容 |
|---|---|
| 职责 | 时间轴、快照、读数序列 |
| 关键决策 | 时间轴是**平台机制**，不是视图的私有状态（C3） |
| 关键决策 | **没有单独的「快照类型」，这是决定而不是遗漏**：需要快照的两件事都已由既有物满足——「留住会被覆盖的迹」由「`Trace` 是值」满足（`RunController` 就是按值返回的，副本即快照，由 `trace.trace.a_copy_is_a_snapshot` 断言）；「记住一条读数从哪来」是溯源（run id + 采样序号），是关于迹的数据而不是迹的副本。真正需要快照的场景是「导出选定时间区间」或「大迹的写时复制共享视图」，两者目前都没有调用者，所以不造 |
| 依赖 | `run`, `store` |

### 4.4 `core/runtime/io/` —— 导出契约

| 项 | 内容 |
|---|---|
| 职责 | 导出接口与格式注册 |
| 关键决策 | 格式全是插件；内核只提供 `FieldBuffer` ABI 与数据集读取 |
| 关键决策 | 预检 `check_export`：**写之前**回答「这个格式留不留得住不确定度」 |
| 依赖 | `store`, `trace`, `abi` |

### 4.5 `core/runtime/file/` —— 整文件读写

| 项 | 内容 |
|---|---|
| 职责 | 读/写整个文件；`absent` 与 `unreadable` 分开；UTF-8 路径到平台打开调用的**唯一**转换处 |
| 关键决策 | 它不在任何一个格式契约里：迹导出器与文档存取契约都要「把字节搬到路径上」，谁托管都会让另一个依赖一个主题不是它的模块 |
| 关键决策 | 失败不得留下半个缓冲区：调用者拿到半份文件时无法与「文件本身就短」区分，而后者看起来就是数据 |
| 依赖 | 无（标准库） |

### 4.6 `core/runtime/instrument/` —— 仪器一等公民（C6）

| 项 | 内容 |
|---|---|
| 职责 | 测量设备的契约、注册表，以及「分度 → 标准不确定度」的框架模型 |
| 关键类型 | `IInstrument`, `InstrumentDesc`, `MeasureContext`, `MeasureRefusal`, `InstrumentRegistry` |
| 关键决策 | **先有契约、后有设备**：C6 的原文是 `IInstrument` 与 `ISimModel` 同时立项、不许后补。`ISimModel` 那一半在本仓库已以 `kernels::IBatchAdvancer`／`execution::IStateOperator` 的形式存在，所以这里不造同名接口去满足一个名词 |
| 关键决策 | **R1 由类型承载**：`measure()` 收裸 `double`（真值）、吐 `UncertainValue`（值+不确定度+量纲）——没有不确定度的测量不是测量，而能返回裸数字的仪器可以把别人给它的真值当成自己测到的 |
| 关键决策 | **承诺 3 是一个函数**：`resolution_uncertainty(w) = w / sqrt(12)`（均匀分布的 B 类评定）。插件可覆盖，但起点是有定义的答案 |
| 依赖 | `units`, `diag`, `store`, `plugin`（宿主取读数走 C4 的故障屏障） |

## 6. 消费者与内容（不在 `core/`）

### 6.1 `views/` —— Qt 界面（可整体删除）

| 视图 | 说明 |
|---|---|
| `qt/nodegraph/` | 节点编辑器。**内置的消费者实现**，不是 `IView` 插件——见下方「视图是内置的还是插件」 |
| `qt/blocks/` | 积木化视图（Scratch 风格）。与节点编辑器投影同一份图 |
| `qt/formula/` | 公式 / YAML 文本视图 |
| `qt/property/` | 端口类型驱动的属性面板（`portui` 的实现） |
| `qt/instrument/` | 仪器读数面板（投影优先：高对比、大字号、色盲安全） |
| `qt/modelconf/` | 模型置信度面板（能量漂移、∇·B 漂移，C8） |

**判据**：四个创作视图投影同一 IR，是同一份图的四种皮，不是四种架构。

**视图是内置的还是插件？** 这个问题有过两个不同的答案，代码里只兑现了其中一个，所以写清楚：

| | 现在的做法 | 许诺的做法 |
|---|---|---|
| 节点编辑器本体 | `views/qt/` 里的**内置消费者**，随 `qp_shell` 静态链接 | `IView` 插件的一个实现（上面的表曾如此声称）|
| 内容插件的影响面 | **它能渲染的东西**：节点类型、端口、类别色、工具提示 | 同上，但更彻底 |
| 「加一个新节点类型要改视图代码吗」 | **不用**——`NodeDesc` 进注册表，画布按名字解析，调色板按 `category` 分组 | 相同 |
| 「加一种新视图（积木/公式）要改什么」 | 改 `views/qt/`，重新编译 | 装一个插件 |

**判据不是「静态还是动态链接」，而是「谁可以依赖谁」。** 铁律是 `core/` 不得依赖 `views/`——它保证 GUI 是
可选前端而不是应用本身，并且可以被机器验证（删掉 `views/` 后 `core/` 仍编译、仍全绿）。这条铁律不区分一个视图
是静态链进去的还是运行时装载的：一个动态装载的视图插件同样住在消费者一侧。所以在 `views/` 里构建节点编辑器
**不违反**任何分层规则，它只是不是「可插拔的视图」。

**真正的缺口，以及它为什么现在不开工。** `Capability::view_items` 声明了、有字符串名（`"view_items"`），
宿主也会协商它——但全仓库**没有 `IView` 接口**，也没有任何视图插件契约，所以这个能力位今天指向一个插件
无法实现的承诺。要让它成真需要：一个 `IView` 接口（生命周期、它拥有哪个布局槽、它向哪个 Qt 容器注册）、
一个视图注册表（`host` 里第五个、或干脆是 `views/` 自己的）、以及一个**跨边界表示一个 Qt 部件的办法**
——而后者与「`core/` 里不得出现 Qt」直接冲突，所以这个接口必须住在消费者一侧、由应用来组合，而不是住在 `core/`。

所以顺序是有意的：**先把唯一的视图做到能用**（本阶段在做的事），再谈视图的可插拔性。一个还没有第二种视图的平台
去设计第二种视图的接口，只会得到从第一种视图的形状里猜出来的接口——而那个接口的第一个真实用户会把
它重写一遍。

**重新开启的条件**：真去写第二种视图（积木或公式）的时候。那时 `IView` 的形状由**两份**实现共同决定，
而不是由一份实现加一段想象决定。

**当前落地**：`qt/node_graph_view`（节点编辑器）、`property_panel`（`portui` 驱动）、
`measurement_panel` 与 `confidence_panel`（测量与置信度）、`editor_window`（装配、File 菜单、Run）。
`blocks` / `formula` 两个视图**未开工**：它们是「同一份图的另外两张皮」，排在内容插件之后——
在只有演示节点库的时候加第二个视图，只会把 paint 代码写两遍。

**节点目录只有一份。** 视图层曾有自己的可枚举容器 `views::TypeCatalog`（当时 `INodeCatalog`
不提供枚举，编辑器需要枚举，容器就写在了调用者那一层）。内容插件出现后这件事的代价才显形：
插件的主要贡献就是节点类型，而唯一可枚举的容器在**消费者**层，插件无处可放。于是容器下沉为
`core/graph/ir::NodeTypeRegistry`，视图层只留下真正属于它的一件事——**面板如何分组**
（`views::by_category`，纯函数，不构造任何 Qt 对象即可断言）。两个容器就是两个「有哪些类型」的答案，
而面板只会显示它碰巧拿到的那个。

**`EditorWindow` 借用宿主，不拥有它。** 构造参数是 `qp::host::PluginHost&`，节点目录与它注册的
内置演示类型都归宿主所有，理由同上：窗口自己持有一份就是第二份答案。演示类型走
`PluginHost::add_builtin_node_type` 而不是直接写注册表，所以它们和插件的贡献一样**可归因**
（`origin_of` 答 `qp.builtin`）**可撤销**——绕过记录的那条路，正是记录要堵的洞。

**C5 是断言，不是印象。** 调色板原本是四个文件里的 `QColor(0x..)` 字面量，「警示文字读不读得清」只能靠
看截图回答、「色盲安全吗」根本答不了。现在它是 `views/qt/theme.hpp` 里的**数据**加两个公式——WCAG 2.1
相对亮度与对比度、以及三种二色觉的线性光模拟——因此由普通 Catch2 套件在**两个编译器**上检查
（`theme.contrast_is_measurable`、`theme.text_clears_wcag_aa`、`theme.meaning_survives_colour_blindness`、
`theme.text_on_a_tinted_node_is_readable`）。把「看着像」换成量出来的数字之后，测试当场抓出三处真实缺陷：
四个品类色在绿色盲下只差 0.019（重新搜索色相/亮度空间，最小间距 0.209）；节点整块填充时**任何**墨色在
`#8C663F` 上最好只有 4.18:1，于是节点盒改成「品类色标题带 + `surface_raised` 正文」两段式；页脚在用
`text_disabled`（2.5:1）承载节点的身份信息。

**图标是数据，资源是派生物。** 位图与「每个墨色字符扮演什么角色」写在 `views/qt/icons.cpp`，角色是
`Palette` 字段而不是字面量（`theme.icons_use_palette_ink` 要求每一个不透明像素都是调色板自己的颜色）。
`scripts/make_icon_sheet.py` 把它们栅格化成一个 53×8 的灰度 PNG（0..3 是调色板下标、`0xFF` 透明），
由 `views/qt/qp_icons.qrc` 打包进 `qp_views`；`theme.icons_match_the_shipped_sheet` 逐像素比较表与图，
所以「仓库里存着一张派生图片」不会变成「图片悄悄过期」。**一个坑值得记下来**：`.qrc` 编译进**静态**库时，
链接器会丢掉没有引用的目标文件，资源因此不会注册，`QImage::load` 在运行时静默失败——库内部必须有一次
对生成符号的引用，且该符号的声明在全局作用域（`Q_INIT_RESOURCE` 在命名空间里会把声明也命名空间化）。
加一个图标是**两步**：写表（`icons.cpp` 的 8×8 位图 + `Glyph` 枚举 + `count()`），再跑一次生成脚本
（`scripts/make_icon_sheet.py`）。第二步忘了会被 `theme.icons_match_the_shipped_sheet` 当场抓住，
而不是表现为「某个按钮没有图标」——这正是把派生资源留在仓库里的理由。

**三处反馈是断言出来的，不是看出来的（本轮）。** 画布此前有三处「能用但说不清有没有用」的交互，全部补齐：

1. **端口悬停。** 抓取半径是 12 **设备**像素（除以当前缩放），所以「这个点够不够近」只有画布能回答；
   把半径再实现一遍的测试只是在断言自己。因此画布把这状态**报出来**：`hovered_port()` / `hovered_node()`
   读的是 `NodeItem` 自己那个驱动绘制的标志，而不是画布旁边另存的一份意图——两份会在某条清除路径上分叉。
   `hover_at(viewport_pos)` 是 `mouseMoveEvent` 调用的同一个函数，公开它使测试无需合成鼠标事件即可断言。
2. **选中邻域高亮。** `prominence_of(node)` / `edge_prominence(i)` / `edge_source(i)` 把「点亮了什么」
   变成可查询的值。**写这条测试时抓到自己一个错误假设**：边的规则是「**任一端**在邻域内即点亮」，
   于是从被点亮的 filter 连向被淡化的 sink 的那条线**仍然是亮的**——它正是选中节点影响传播的那根线，
   把它淡掉等于切断了高亮本身要展示的连接。第一版测试期望它变暗，实测把它纠正了。
   `kDimmedProminence = 0.35` 同时是公开常量与绘制代码用的那个数：测试有自己的 `0.35` 副本，
   绘制代码一改它就永远不再失败。
3. **读数行 → 产生它的节点。** 闭环此前只有一个方向（图 → 数字）。新增
   `MeasurementPanel::reading_selected(NodeId)` + `EditorWindow::measure_selection()`：从选中节点的迹里
   取**最后一个采样**记为一条读数，`Measurement::Source` 记住它来自哪个节点；点表格某行则 `reveal` +
   `select_node` 那个节点。**维度按通道的维度挑，不按位置**——`Dataset::add` 会把读数的维度归一化成
   数据集的维度，所以按 `values[0]` 取值会把速度当长度存下来，而那是一个被当作测量结果的错数。

**一个「全绿但退出码非零」的缺陷，值得单独记。** 上面第 3 项做完后，测试套件的每一条断言都通过，
进程却以 `0xC0000005` 退出。成因：`QGraphicsView` 在**析构**时清空它的 `QGraphicsScene`，清空场景会发出
`selectionChanged`，画布把这个信号转发成 `node_selected`，而窗口把它接到属性面板——于是**画布的析构函数
重建了兄弟面板的控件**，能否存活取决于 Qt 先销毁窗口的哪个孩子。修法不是给处理器加空指针判断：
处理器运行时已经没有正确答案可给（它要对话的面板可能已经不存在），诚实的做法是让画布在自己的条目被拆开
**之前闭嘴**，于是有了 `NodeGraphView::go_quiet()`，`~EditorWindow` 的第一条语句就是调它。
一个绿色的报告配一个非零的退出码，比一个红色的报告更糟——它的结论错在「没事」这个方向上。

**`clear_selection()` 是补上的一条 API，不是测试的便利。** `select_node({})` 读起来像「取消选择」，实际是
查不到该 id 的空操作（契约如此写、也如此实现），于是调用者**没有办法撤销**一次选择，高亮成了一个进得去
出不来的模式。第一条测试用 `select_node({})` 做取消，断言的是一个「仍然被淡化」的图，这正是测试该抓住的
假设，而不是该包含的假设。

**第三处布局缺陷，以及一个把截图读错的教训。** 读数表的第四列「status」在运行窗口里**看不见**——
`kDockWidth` 是 320，而四列（`#`/`value`/`uncertainty`/`status`）需要约 420。status 列正是说明一个数算不算
数的那一列，也就是这个面板在一层之下的全部意义，所以挡住它的宽度等于挡住了那个功能。改成 420 之后仍然
不对，而原因不是那个常量：`QDockWidget` 按**子控件的 sizeHint** 定尺寸，而 `QTableWidget` 的 hint 随内容
增长，于是窗口变宽时多出来的宽度进了停靠面板而不是画布——实测 1680 逻辑像素的窗口里停靠占了 892，画布
只剩 692，这不是任何外部 `resizeDocks` 能修的比例。修法是给两个面板各设 `setMaximumWidth(kDockWidth)`：
它们都是列数固定的表，更宽一点用都没有，而那些宽度全部来自画布。

**截图这一次骗了我，值得记下来。** 上面那段诊断过程里，我反复从截图里得出「停靠面板不见了」，而
`main.cpp` 里临时加的几何打印说得很清楚：`DIMM dock Measurement visible true geom QRect(860,59 420x335)`，
两个面板都在、宽度正是 420。真正发生的事是**这台机器的显示缩放**——Qt 按 1280 逻辑像素布局，屏幕上按约
1.44 倍的设备像素比呈现，于是那几个窗口实际需要约 1843 物理像素宽，而屏幕只有 1707，右边缘被推到屏幕外。
所以「看不见」是截图的属性，不是窗口的属性。教训不是「少看截图」——本阶段的另外三处缺陷全是截图抓到的，
而这一处不是；教训是**截图只能证明「看见了什么」，不能证明「不存在」**，否定性的结论要有一个非像素的
证据（这里是窗口自己的 `geometry()`）。

**当前落地**：`formats/qpjson`、`formats/csv`、`mechanics`（RK4 积分器 + `MechanicsBinder`）、
`instruments`（四台测量器件）、`analysis`（加权最小二乘 + 不确定度传播）、`models`（阻尼振荡器 / 单摆 /
抛体 + `ModelsBinder`）。
`views_items` / `experiments` / `examples` **未开工**，
它们是内容而不是框架——框架侧的判断是「这些目录是否需要新的接口才能写」。见第 9 节的框架完成度审计。

**`models` 填的是一个拒绝而不是一个空缺。** `mechanics` 的算子积分的是**无阻尼**的 `x'' = -w^2 x`，它的
binder 刻意拒绝 `c != 0` 的节点（「内核没有阻尼项」）——那是对的，也正好说明了一个真正缺失的模型：阻尼振荡
是力学实验里最先测的东西（衰减率就是那个测量），而用户当时无处可填那个数。所以新目录不是重复 `mechanics`，
是补上它明确拒绝过的那一半。

**四个模型共用一个 RK4，而状态布局故意不同。** 四阶步进是同一个算法作用于 `y' = f(y)`，写三遍就是三处
系数可能写错、三处在想换五阶时要改；所以每个模型只是一个右端加上它自己的声明。布局不同则是因为**布局是模型
自己的事**：单摆没有「频率」参数，它的周期随振幅变化，那正是单摆与谐振子的全部区别，为了让形状一致而填一个
无人读的分量是凭空发明一个参数。每个 binder 因此声明它需要的布局并拒绝其它，这也是三个模型能共存于一张图的
原因。

**第四个模型是受迫振荡器，而它证明了布局由模型拥有这条规则不是装饰。** `x'' = -w0^2 x - gamma x' + F cos(wd t)`
是**非自治**的，直接写法是读一个时钟——而读墙上时钟的模型无法从种子复现，读运行循环自己步数的模型是在拿它不
拥有的状态（`IStateOperator` 明文禁止：一步只能依赖状态与 `dt`）。所以相位作为状态的第三个分量，`t' = 1`，
方程重新自治。它的分量数是 3，与无阻尼振荡器相同而**理由不同**（那一个的第三槽是频率，这一个是时钟）：
两个模型共享一个分量数不是可以依赖的巧合，而 `can_bind` 逐类型地问，正是「分量数是逐类型的事实」的含义。
它声明自己**不可逆**，而原因不是物理而是时钟——状态里带着一个有起点的绝对时间，就无法倒着越过那个起点。
物理用例是共振实验，与稳态幅度的闭式解比较：共振点、两侧各两点，以及时钟确实推进。零驱动频率那一点
（静态弯曲 `F/w0^2`）第一次量出来只有一半，**记录在测试里而不是改容忍度**，随后查清：**是测量工具错了，不是
模型错了**——`wd = 0` 时响应是一个常数偏移，其峰峰值是残余的瞬态涟漪而不是弯曲，而当时的辅助函数返回的正是
半个峰峰值；对线性受迫振子，窗口内的**均值**才是对的工具（瞬态按 `exp(-gamma t/2)` 衰减、`cos` 在整数个周期
上的均值为零，所以窗口均值就是稳态响应自身的均值），换用它之后静态弯曲恢复到 0.5% 以内。两件事因此值得并排
记下：**记录一个未解释的偏差比改容忍度好，而记录之后要把它查清**——这次查清的结果是模型一直是对的。

**抛体的可逆性声明值得读两遍。** 它的方程和振荡器一样是**线性**的，按方程看应该可逆；但它声明自己
**不可逆**——因为「它在地面停下」是模型定义的一部分，而停下不是一个能倒着跑的运算。**声明是关于「如此陈述
的模型」，不是关于孤立的微分方程**，而这正是插件作者会写错的地方。另两处一并记下：`diag` 的错误码没有被
新增（`fit_failed` 早就在，见 §9.5），以及**契约门禁自己在这次改动里暴露了一个缺陷**——它的
`--only` / `--exclude` 用子串匹配路径，于是 `--only model` 因为 `model` 是 `models` 的前缀而选中了
`tests/unit/plugins/test_models.cpp`，两个分区同时认领同一批用例、各自把对方合法的用例报成孤儿。修法是给两种
写法两种语义：**带分隔符的是片段**（子串匹配是它的定义），**裸词是名字**（逐分量相等）。回归夹具写在自检的
**临时树**上而不是真实树上——只靠今天恰好有哪些目录而成立的性质，下一个加目录的人就会看到它失效。

**`analysis` 是「冻结的契约」这句话第一次被兑现。** 见 §9.5：`FitResult` 在有第一个实现之前就冻结了，
当时的判断是「契约必须在有第一个实现之前定下来，否则第一个实现会顺带定义契约」。本阶段条件到来，而
**契约一个字没动**——没有新接口、没有新能力位，`plugins/analysis` 是一个新目录加一个 CMakeLists。
唯一的 `core/` 改动是 `diag` 补了一个错误码 `fit_failed`，而那不是为了让新模块能编译，是为了让一条失败
信息指向正确的地方（见下）。

**拟合的数值选择，以及它们各自被什么测出来。** 正规方程会把条件数平方，所以诚实的问法是「横坐标靠得
多近就不行了」，而不是「这样写行不行」。用例 `fit.analysis.nearly_equal_abscissae_still_fit` 在 1e-4 的
横坐标跨度上（比任何实验夹具都差三个数量级）量了它，并额外断言协方差**有限**——只断言「系数看起来对」
会漏掉一个数值上无穷大的逆矩阵。奇异系统按 Cholesky 的主元判定而不是行列式：行列式是 n 个数的乘积，
在矩阵真正奇异之前早就下溢了，于是会拒掉一个动态范围大但条件良好的系统。R² 在「所有 y 相同」时**缺席**
（0/0 不是 1），约化卡方在自由度为 0 时**缺席**（那会读成完美拟合）。

**三处测试自身的错误，都是被实测纠正的**，值得并列记下来，因为它们的形状各不相同：（1）断言
`chi_squared == 0` 与 `is_exact()`——正规方程由乘积求和的系数带几个 ulp 的误差，残差量级 1e-16，
**精确为零是错的期望**；改成断言残差远小于读数自身的不确定度。（2）断言 `abs(ten - sigma/10) > 1e-3`
——按 n 除而不是按 sqrt(n) 除，得到的是 1/sqrt(n) 倍而不是 sqrt(n) 倍，那个不等式**根本是假的**；
改用比值，并在改的过程中又写错一次（拿比值去和 sqrt(10) 比），所以现在断言里明确写出「1/sqrt(n)」。
（3）相关的差值用例里系数顺序写反，把 `c0+2c1` 减 `c0+c1` 写成了反过来，值成了 -1；而且我一开始拿
`combine` 的对角线情形当「独立算法」来对比——那其实是**同一套算术**，两边当然都是 0.01。真正该比的是
两次单独求值的误差棒（0.71），相关系数把差值的不确定度压到 0.01 才是这个函数存在的理由。

**`instruments` 是第一个「已声明、已测试、但从未接线」的模块被接上的例子**，值得完整记下来，因为它的形状
在本仓库反复出现。`core/runtime/instrument` 有一份完整契约（`IInstrument` 四方法、`InstrumentDesc`、
`MeasureContext`、三个拒绝码）、一个注册表、一条 C4 要求的故障屏障 `measure_guarded`、以及**十三个通过的
测试用例**——而全仓库**没有任何生产代码注册过一台器件**。`PluginHost::add_instrument` 存在、被测试夹具
调用过、从没被 `plugins/` 里的任何东西调用过。
这不是「还没写」，这是**一个承诺在文档里成立、在测试里成立、在运行的程序里不成立**：平台的中心闭环
（测量→记录→不确定度→报告）可以从夹具到达，从别处到达不了。

接线的第一步是补 `PluginHost::add_builtin_instrument`：只有 `add_instrument` 时，一台器件必须来自一个
被装载的插件，于是一个没有插件的构建**没有任何仪器**，而「测量」这件事就不可达。器件的内置路径与节点
类型的内置路径同形，进同一个账本、同一个 `origin_of`、同一个 `clear_builtin_*`。第一版
`clear_builtin_instruments` 把整个内置账本重置了，于是清空仪器会**连带清掉内置节点类型**——窗口为了
登记第二批器件而清空仪表架，代价是调色板空了，而表现形式看起来像别处的注册 bug。测试
`host.a_builtin_instrument_is_attributed_and_removable` 就是为这条而写的。

四台器件的误差模型只有一条，而且是**测量学上正确的那一条**：读数 = 真值按分辨率取整，不确定度 =
`resolution/sqrt(12)`（矩形分布，宽 w 的均匀分布标准差是 `w/sqrt(12)`）。这条模型给出的数字本身就是这门课
的教学内容：

| 器件 | 分度 | 标准不确定度 | 学生通常写的 |
|---|---|---|---|
| 米尺 | 1 mm | 0.29 mm | "0.1 mm" |
| 游标卡尺 | 0.05 mm | 0.014 mm | "0.05 mm" |
| 数字秒表 | 10 ms | 2.9 ms | "1 ms" |
| 毫伏表 | 0.1 mV | 0.029 mV | "0.01 mV" |
| 安培表 | —（不是分度） | 随读数变 | “1%” |

右列是这个平台存在要纠正的习惯：那是「误差棒来自仪器」与「误差棒来自显示屏最后一位」的差别。**刻意不加
随机噪声**：读数带不确定度，如果器件还抖动，那个抖动就是报告的不确定度覆盖不了的误差——数字与它自己的
误差棒自相矛盾，正是本平台要抓的失效模式；而重复测量本就该重复，实验室里的离散来自人和装置，不来自一台
每次问你都给不同答案的仪器。`measure_guarded` 的用例在**真实器件**上跑了一遍：一台器件从不通过故障屏障
被调用，就是一台失败路径没人处理的器件。

**两个「类型不许被搬动」的教训。** `IInstrument` 删除了拷贝（两台器件自称同一个 id，就是同一个问题的两个
答案），而删除拷贝会**隐式删除移动**——于是 `std::vector<GraduatedInstrument>` 无法编译，报错出现在
MSVC 的 `std::construct_at` 里，指向标准库而不是指向原因。器件 rack 因此是**就地构造**的 `std::array`：
固定大小、不搬迁、大小是编译期事实。第一次尝试还有第二个错：在 lambda 里构造数组再返回，`std::array` 的
隐式移动是逐成员定义的，元素类型不可移动就整个数组不可移动，而返回值优化**不覆盖被返回聚合体的成员**。
结论不是「换个写法」，而是「器件的地址就是它的身份」——注册表持非拥有指针，一台被搬动过的已注册器件会留下
一个回答默认分辨率的空壳，而且没有任何东西会说明出过错。

**第五台器件证明了那条重新开启条件，而它的形状值得单独记下。**
`ruler.hpp` 的文件注释结尾不是一个猜想，而是一条条件：若出现一台误差模型
**不是量化** 的器件，它应该直接从 `IInstrument` 派生。安培表就是那台器件，而它接上时
**接口一行未改**：规格写作 `+/- (p*|读数| + c)`，读数就是真值（不量化），不确定度是
`(p*|读数| + c)/sqrt(3)`。两个系数回答两个不同的物理原因：`p*|读数|` 是增益误差，它与被测量成比例，
所以“3%”在近零处毫无意义；`c` 是零位与噪声，它不在乎读数是多少，所以“3%”在满量程处
毫无意义。**分母同样是 `sqrt(3)`**，因为 `+/- x` 是一个界，而界不是标准不确定度；把半宽当标准差直接相加，差的就是 73%。

它同时让 rack 变成了一个**真的集合**：此前它看上去是一组器件，实际上是一组分度器件。
新的断言因此写成**对比**形式：米尺在 2 mm 与 0.02 mm 上报同一个不确定度，安培表则报两个。
各自验证自己算术的用例做不到这件事：两种模型写成同一个时，它依然会过。

**三处实现级的错误，形状各不相同，都记在代码里。**
（1）**声明了名字的局部变量被当成了存储**：第一版 `build_rack` 在函数里建五个局部器件、返回
`{&它们...}`，于是每个指针在右花括号处悬垂。它**编译通过、看上去正确**，而诊断是一条 `SIGSEGV`，
发生在名字里写着“本构建携带的器件可用”的那个用例上，而且是在后一次调用的 vector 把栈上那块
内存覆写之后——**悬垂指针的症状出现在它被写坏的时刻，不是它被创造的时刻**。修法不是“小心一点”，而是让
存储和指向它的指针是**同一个对象的成员**。
（2）**`std::optional<T>` 也不行**，而它的报错点在标准库里：`optional` 自己的移动构造函数要求
`T` 可移动，而器件的移动是故意删除的。`std::make_unique` 同理：它把参数转发进一个**按值**构造的 `T`。
最后的形状是 `std::unique_ptr<T>(new T(...))`：移动的是**指针**，器件一步不动。
这也把第（1）条的危险变成了结构上的不可能：构造函数**无法**返回一个指向它自己拥有的值的
指针，因为它根本不拥有它。
（3）**新器件的 `resolution_` 默认成了 `1.0`**，而它本该是 `desc.finest_resolution`。两个用例同时变红，
而报文看不出原因（一个报“0.00029 > 0.2887”，另一个报“1.0 == 0.000001”）；真正说明问题的是第三个：
`set_resolution(1e-6)` 被一台“最细分辨率就是 1e-6”的器件拒绝。
**一个任何器件都不想要的默认值，就是能把漏写藏起来的那种默认值。**

**第三个教训与编译器有关，不是与代码有关。** 校准偏移的用例原本断言
`measure(0.024).value == 0.026`，在 MSVC 上过、在 32 位 GCC 上不过，展开值两边**都显示 0.026**。成因是本仓库
早已记录的那一条：MinGW 目标是 i686，`FLT_EVAL_METHOD == 2`，表达式在 x87 的 80 位寄存器里求值，而字面量
`0.026` 在编译期就已经舍入成 double。于是「和字面量比位」这个写法测的是编译器而不是器件。改法是**用器件
自己的分辨率**构造期望值（那是它自己乘过的那个 double），断言保持**精确**——退化成容差会让测试不再能区分
「落在刻度上」与「落在刻度附近」，而那正是这台器件的全部契约。

**器件已经能选了，读数也就真的来自仪器。** 测量面板多了一个下拉列表（内容来自 `PluginHost::instruments()`
——面板不自己去取注册表，理由与窗口借用宿主的节点目录是同一条），`show_devices` 填它、`chosen_device()` 按
**id** 而不是指针回答。用 id 是有意的：器件可能在面板还显示着它的时候被卸载，存一个 `IInstrument*` 就是
第一次读数时的悬垂指针；调用方拿 id 去问注册表，而只有注册表知道它还在不在。

`EditorWindow::measure_selection` 随之改了两处，两处都不是外观：

1. **通道按仪器的量纲挑，而不是按数据集的**。游标卡尺量的是长度，所以它读的是以米为量纲的那条通道；
   按数据集的量纲挑会让一台「量时间」的器件去读位移，而 `Dataset::add` 会把这个读数**静默归一化**成米。
2. **读数真的经过器件**，并且经过 `measure_guarded`——器件是插件代码，一台会抛异常的器件不能把进程带走。
   交给器件的真值是模型自己的值，而它**自带的不确定度被丢弃**，这是刻意的而不是疏忽：这里记录的是「对该
   值的一次读数」，所以误差棒属于仪器的分度而不属于仿真。学生用真实卡尺去量一个仿真长度，得到的是卡尺
   的不确定度——那正是他们该学的东西。状态栏把两条路径分开说：「as the trace has it」与
   「measured with the Vernier caliper (+/- 1.44e-05)」，因为一个数是怎么来的，是它声称的一部分。

没有器件的构建退化为原来的行为（按数据集量纲取迹的最后一个采样），并且**状态栏说明了是这条路径**——
一个把两条路径都叫「recorded」的状态栏会把上面那个区别藏起来。

**动态装载已经真的接上了。** 在此之前，「插件即内容」只对一个**构建**成立：内容靠
`QP_HAS_*` 宏静态链进 `qp_shell`，仓库里没有任何代码调用过 `load_plugins`。现在
`views/app/main.cpp` 构建一个 `qp::host::PluginHost`，扫描 `QP_PLUGIN_DIR`（未设置时为可执行文件旁的
`plugins/`），按 manifest 位协商能力，把装载结果逐条报到 stderr，并把宿主自己的节点目录交给窗口。
静态链接的内容与目录里装载的内容进的是**同一组注册表**，这才是「万物皆插件」作为平台属性而非构建属性。

**能力授权写在 `main` 里而不是取 `kKnownCapabilities`**，这是决定而不是啰嗦：一个把自己知道的全部
都授出去的宿主拒绝不了任何东西，于是「这次会话允许做什么」就由「现场有哪些插件」回答。
`field_domain` 与 `render_domain` 目前不在授权里，因为没有内容贡献它们；加一个贡献它们的插件，
就是在这里加一位。

### 6.3 `tests/` `bench/`

见 `standards/test-taxonomy.md`。注意 `tests/contract/` 是**契约合规套件**所在地，
它与插件接口**同时提交**，是新增接口的强制配套物。

## 7. 下推规则（本文件如何继续细分）

```
docs/plan-tree.md          ← 本文件（到模块级）
    └─ core/<layer>/<module>/spec.md       ← 模块规范：类型契约 + 接口签名（到类型级）
          └─ core/<layer>/<module>/functions.md  ← 函数契约（到函数级）
                └─ include/qp/.../*.hpp     ← 头文件里的契约注释（与代码同源）
                      └─ tests/...          ← 每个 @tests 条目的实现
```

### 不可颠倒的顺序

```
(1) 类型契约  →  (2) 接口签名  →  (3) 函数契约  →  (4) 实现  →  (5) 测试
   （冻结）      （冻结）       （逐模块推进）
```

> **同一模块内，类型先冻结；不同模块间，下一层的类型定型前不写上一层的函数规范。**

理由：把 `graph.connect()` 的签名先写死、而 `PortId` 还没定型，
那份规范 100% 会返工，并带着下游几十个函数一起返工。

### 进度如何记录

`plan-status.json` 记录每个模块的下推深度：

| 状态 | 含义 |
|---|---|
| `planned` | 只有模块级描述（本文件） |
| `contract` | 类型契约已冻结（`spec.md` 就位） |
| `specified` | 接口签名 + 函数契约就位（`functions.md` 就位） |
| `implemented` | 实现完成，测试通过 |
| `verified` | 全部测试 + 门禁 + 覆盖率证明义务通过 |

## 8. 依赖规则（CI 强制）

允许的依赖方向（箭头 = "可以依赖"）：

```
units ← diag ← ports ← reflect
                 ↑
              abi ┤
                 ↓
        ir → structure → mutate
                 ↓
              eval → domain → kernels
                 ↓
              field
─────────────────────────（core 边界：以下禁止被 core 依赖）
runtime → authoring
            ↑
        persist（document + structure：格式是插件，契约是地基）
─────────────────────────
host  ← plugin + capability + ir + kernels + instrument + io + file
        （组合根：唯一允许扇入这么宽的模块；除应用外无人依赖它）
─────────────────────────
views, plugins        （消费者，core 不得 include）
```

> `runtime/` 内部另有两条不越过上图的边：`instrument` 依赖 `store`（一条读数**就是** `UncertainValue`，
> 另造一个平行类型正是本项目反复避免的「两份表示」），`eval`/`execution`/`instrument` 依赖 `plugin`
> 以取得 C4 的故障屏障——`plugin` 是 L0，这是向下依赖而非倒置。

### 五条铁律

1. **`core/` 不得包含任何 Qt 头文件。** 错误类型、注册表、求值器全部与 Qt 无关。
   Qt 只在 `views/`、`plugins/`、宿主可执行文件中出现。
2. **`core/` 不得包含 `views/` 或 `plugins/` 的头文件。**
3. **`core/` 不得依赖 Eigen 之外的第三方**（Eigen 仅允许出现在 `eval/` 与数值内核接口后方）。
4. **`units` 与 `diag` 不得依赖 core 内任何其他模块。**
5. **热路径函数禁止抛异常、禁止分配、禁止虚调用**（由 clang-tidy 自定义规则检查）。

## 9. 尚未开工的部分，以及各自重新开启的条件

> **目的。** 一个「还没做」的清单如果只写「未完成」，读者无法判断那是**待办**还是**决定不做**，
> 于是要么重复追问，要么自己去补一个不该补的东西。所以每一项都写三件事：现在有什么、缺什么、
> **什么条件下才该动手**。第三项是这里最要紧的一栏——它把「以后再说」变成一条可以核对的判据。

### 9.1 内容插件：`plugins/models` `instruments` `analysis` `views_items` `experiments` `examples`

**现在有什么**：`plugins/formats/qpjson`、`plugins/formats/csv`、`plugins/mechanics`
（RK4 积分器 + 阻尼/其他积分器的拒绝理由 + `MechanicsBinder`）、`plugins/instruments`
（米尺 / 游标卡尺 / 数字秒表 / 毫伏表，以及 `mount_instruments`）。

**缺什么**：具体物理模型、拟合与不确定度传播、渲染项、教师层实验描述、示例图库。器件这一侧则已经接通：
`plugins/instruments` 的四台器件登记进宿主，测量面板可以选，`Measure` 的读数**经过器件**产生并带上它的
分度所蕴含的不确定度。

**为什么现在不做**：这些是**内容**，而框架对它们的判断标准只有一条——「写它们是否需要新的接口」。
目前不需要：`NodeTypeRegistry` 收节点类型、`IInstrument` 收设备、`IBatchAdvancer` 收算子、
`IExporter`/`IDocumentFormat` 收格式、`host` 把它们装进注册表。加一个单摆模型或一台游标卡尺，
是往现有接口里填东西，不是改接口——`plugins/instruments` 就是这条判断的一次实测：写四台器件没有新增
任何接口，只新增了 `PluginHost::add_builtin_instrument`，而那是**宿主**的一侧（只有 `add_instrument`
时，一台器件必须来自被装载的插件，于是没有插件的构建就没有仪器）。

**重新开启的条件**：
1. **某类内容写不出来**，而不是「还没写」——例如一个需要偏微分方程残差作为一等输出的模型，
   或一台需要在校准曲线之间插值的仪器。那说明接口缺一个概念，是框架的活。
2. **`analysis` 需要一个 `FitResult` 的生产者/消费者闭环**：`runtime/store` 里 `FitResult`
   的结构已就位（系数 + 协方差 + 残差 + R²）且是冻结的，但全仓库**没有任何东西产生或消费它**。
   第一个真实需求出现时，改的是那个缺口所在的一侧，而不是先写一个没人调用的拟合库。
   ——**已兑现**：`plugins/analysis` 是生产者（加权最小二乘）也是消费者（`combine_correlated` 读协方差），
   而 `FitResult` 与 `store` 一个字没改。见 §9.5。
3. **`experiments` 需要教师层的实验描述**（章程 L1 教师层）。它是 YAML，格式本身是插件，
   所以开工的前置是「先有一个把 YAML 读成 `Manifest`/图的东西」——也就是 `authoring/persist`
   之外的第二个格式消费者。
4. **`views_items` 需要渲染域**：`host` 目前**不授权** `render_domain` 与 `field_domain`
   （见 §6.2），因为没有内容贡献它们。第一个渲染项插件出现的同一次改动里，`views/app/main.cpp`
   的授权要多两位——这是有意的摩擦，不是遗漏。

### 9.2 视图：积木视图与公式/YAML 视图

**现在有什么**：节点编辑器（`qt/node_graph_view`）、属性面板（`portui` 驱动）、
测量面板、置信度面板、`editor_window` 装配。

**缺什么**：`qt/blocks`（Scratch 风格）与 `qt/formula`（文本视图）。

**为什么现在不做**：判据是「四个创作视图投影同一份 IR，是同一份图的四种皮」。前两张皮已经把
「一张图 + 一个会话 + 一个撤销栈」这条路走通了，第三、四张皮**不会发现新的架构问题**，
只会把 paint 代码写第二遍。真正需要它们的时刻是**教学内容**需要它们。

**重新开启的条件**：一个具体的教学场景要求非节点表达——例如「学生用公式写 `x'' = -ω²x`
并把它与节点图互相对照」。那是一个**课程需求**，不是架构需求，所以由课程侧提出。
架构侧的准备已经完成：`authoring/commands` 的命令总线是唯一变异入口，任何视图接上它就能共享撤销栈。

### 9.3 `core/authoring/layout`：算法注册表已就位，一个算法都没有

**现在有什么**：`ILayoutAlgorithm` 契约 + `LayoutRegistry`（注册/查找/列举/卸载），
以及 `tests/unit/authoring/test_layout.cpp` 里的三个**桩**算法（网格、带种子、会拒绝的）。
也就是说：接口是**被测过的**，只是没有产品算法。

**缺什么**：分层（Sugiyama）、力导向、径向——任何真实算法。

**为什么现在不做**：算法是内容。更要紧的是**没有消费者**——`auto_layout` 的调用方是视图，
而节点编辑器的画布目前把节点放在用户拖到的位置（`document.layouts()["graph"]`），
这恰好是「算法是插件」这句话里的一个合法答案：**「用户放哪儿就哪儿，别再动」**。

**重新开启的条件**：
1. 画布需要一个 **「整理布局」按钮**，或
2. 打开一份**没有布局槽**的文档（例如别人手写的 YAML 图）时需要给出坐标。
   两种情况下要做的都是「注册一个 `ILayoutAlgorithm` 并在视图里接一个动作」，
   而 `layout` 的契约不需要改——这就是它现在就该存在、而算法现在不该写的原因。

### 9.4 `core/reflect`：接口与测试齐备，没有生产调用方

**现在有什么**：`type_name<T>()`、`unit_symbol<D>()`、`enum_names<E>()`，带自己的契约与测试。

**缺什么**：**调用方**。目前 YAML/脚本/诊断各自拼自己的名字，`reflect` 是那个「应该」的唯一来源，
但还没有人问它。

**为什么现在不做**：它的价值在**第二个**消费名字的地方出现时才兑现——一个名字来源有意义，
是因为有两处必须一致。现在只有一处（`ports` 的端口类型名），所以它还不承担职责。

**重新开启的条件**：出现第二处需要同一份名字的地方。最可能的是
`authoring/persist` 的 YAML/JSON 写出与「脚本接口」，或者一个需要把 `ValueKind` 印成用户可见字符串的
面板。届时改的是**那些调用方**去问 `reflect`，而不是 `reflect` 去追它们。

### 9.5 `runtime/store` 的 `FitResult`：**已闭环**（生产者与消费者都有了）

**现在有什么**：`FitResult`（系数 + 协方差 + 残差 + R²）与 `Measurement`/`Uncertainty` 的三态
（unknown / exact / standard）——这是闭环里「报告」那一半的数据形状，且已冻结。
**`plugins/analysis` 现在是它的第一个生产者**：`fit_polynomial` 与 `fit_linear_model` 做加权最小二乘
（正规方程 + Cholesky），`reduced_chi_squared` 读它；`propagate.hpp` 读协方差矩阵——`combine_correlated`
就是「为什么协方差必须是完整矩阵而不是对角线」的答案。

**缺什么**：显示它的面板（测量面板上的拟合栏）。

**为什么现在不做**（剩下那半）：面板是**视图**，而视图的前提是内容已经在跑；拟合本身已经可用、已被测、
已经由 `qp_test_plugins_analysis` 的十六个用例覆盖。加一栏要动 Qt 层，那是另一件事。

**重新开启的条件**：一次实验需要「把拟合结果写进报告」而不只是算出来。那时要做的是测量面板加一栏，
读的是**已经存在**的结构。

**这条记录本身是本仓库最有用的一条，因为它已经兑现了。** 当时的判断是「结构先冻结是对的——它是契约，
而契约必须在有第一个实现之前定下来，否则第一个实现会顺带定义契约」，并写下重新开启的条件是
「一次实验需要线性回归」。条件到了，而**契约一个字没动**：没有新接口、没有新能力位，`core/` 里**一行
都没改**，`plugins/analysis` 是一个新目录加一个 CMakeLists。这就是「冻结的契约」这个说法的凭据，
而不只是一句期望。

**连错误码都不用新增。** 奇异拟合一开始借用 `invalid_argument`，而 `invalid_argument` 会把「你的输入表格
有问题」这个结论说给一个表格完全正确的调用者——点是有限的、sigma 是正的、点数够多，而正规方程组仍然
不确定它的系数（每个横坐标都一样）。改用 `fit_failed` 就对了，而**它自 `diag` 错误通道写成那天就在**
（`6faf814`）。所以本次 `core/` 的改动量是**零**。一个分域编码的错误通道，在一年后的第一个新消费者面前
正好已经有合适的码，说明当初把码当成一份**需求清单**而不是当成当下需要的东西来写，是对的。
（写作时这一段本来写的是「本次唯一一处 core 改动是新增 `fit_failed`」——那是错的，`git log -S fit_failed`
一次就能查出来。文档里说「本次改了 core」之前应该先查一遍。）

### 9.6 动态插件的细粒度能力

**现在有什么**：`authoring/capability` 的字符串键协商（namespaced id + needs），
以及 `host` **自己合成**的 provider——offers 是 manifest 位的名字，`needs` 就是那份声明。

**缺什么**：一个**动态插件**自己提供 `ICapabilityProvider` 的能力。`PluginExports` 只带
位与两个回调，没有地方放一个虚接口指针。

**为什么现在不做**：补上它要动插件 ABI（`PluginExports` 加字段 → 升 `kExportsVersion`），
而收益要等到有插件真的需要「声明一个 manifest 位表达不了的能力」时才出现。

**重新开启的条件**：出现一个需要以字符串键声明能力的插件——例如「我提供 `qp.io.export_dataset`，
所以别的插件可以来问谁导出数据集」。那时的改动是：`PluginExports` 加一个
`const ICapabilityProvider* (*capabilities)()`，升 `kExportsVersion`，并在 `host` 里优先用插件自己的
provider、退回合成的那个。**这是一个 ABI 变更，所以它必须由一个真实需求推动**，而不是为了对称先做。

### 9.7 画布字号与缩放（已修，记下改法）

**原来的问题**：调色板把颜色与对比度变成了契约之后，**每一处文字都通过 WCAG AA**，但截图复核说「小」。
两者不矛盾：调色板管的是颜色，字号与缩放从来没有人管过——节点盒用的是 Qt 的**默认字体**（96 dpi 下 9 pt，
约 12 设备像素），在笔记本的设备像素比下端口标签只有约六个物理像素高。C5 三条里的「大字号」这一条当时
没有可断言的形式。

**改法（三处，都在 `views/qt/node_graph_view.cpp` / `.hpp`）**：

1. **字号显式化，盒子由字体量出来**。`kTitlePointSize = 10`、`kLabelPointSize = 9` 是权威数字，
   `NodeMetrics` 用 `QFontMetricsF` 从**实际解析到的字体**推出头部高度、行高与整盒高度——Qt 报的是设备
   像素，所以在 144 dpi 的屏幕上同一个点数会得到更高的行、更大的盒子，这正是「大字号」在那台机器上应有的
   含义。先前的失败模式是：常量各自独立，改一个点数字号而盒子不变，文字被裁掉。
2. **回退布局从四列改成两列**。四列比画布宽，于是每个新图都被 `fitInView` 缩小，而缩小的那一步恰好把
   刚调好的字号还回去了。两列是在**默认画布宽度下 1:1 放得下**的最大列数，所以常见情形（几个节点、还没
   存过布局）就是按作者尺寸画的。`kNodeWidth = 188`、`kColumnGap = 30`、`kMargin = 28` 是按**画布真正的
   宽度**（1280 窗口下约 484 像素，被分割器、调色板和属性面板切掉之后）量出来的，不是按窗口标称宽度。
3. **`frame_graph` 加了缩放下限 `kMinimumScale = 0.85`**。原来只钳上界（不放大过 1:1），下界是无限的：
   放不下的图就被一直缩小，直到那一步把字号的意义抹掉。现在超出视口的图按 0.85 画并**滚动**，
   `all_nodes_are_visible()` 如实报告看不全——「更小但完整」不再是无条件的默认。

**新增的断言**（`qt.views.canvas.a_node_box_holds_its_type`）：盒子高度 ≥ 由字体量出的最小值；在**应用真实
给出的画布尺寸**（484×610）下缩放恰为 1.0 且三个节点全可见；画布缩到 280×290 时缩放不低于下限。第三条
是截图查不出来的那条——没有它，「文字是 10 pt」在绘制代码里为真、在屏幕上为假。

**同一个案例里被量出来的两个先前看不见的缺陷**：`itemsBoundingRect` 的左边比节点位置左出 `kPortRadius`
（端口桩），而场景矩形与取景用的是各自算的边距，于是端口桩被判成「在图外」；以及端口行数与盒子高度没有
关系，第四个端口会画到盒子外面。现在端口行数有 `kPortRows = 3` 的上限并**写明**这是限制（节点描述符面板
列出全部端口），而不是让盒子随插件描述符长高——那样同类型的两个节点会不一样高，布局算法就没有稳定输入了。

### 9.8 图求值已就位但未接线（连接解析的剩下那一半）

**现在有什么**：`core/graph/eval` 的 `evaluate_graph` **完整解析节点间的连接**——按 Kahn 拓扑序（同层按槽位
下标破平局）走图，每个输入端口查入边，有边就取上游节点的输出值、无边就退回本节点自己的参数、两者都没有就
表示"未计算"；解析出的输入并入内容寻址缓存键，所以上游一变只有下游重算；输出按插件自己的声明校验后才入
缓存。13 个针对性用例覆盖链式传播、菱形只算一次、bypass 直通、缓存命中、失效范围与三种失败。

画布这一侧本阶段补齐：连线画在**端口桩**上（输出实心、输入空心），拖动节点时线跟着走，并且可以直接用
鼠标从一个输出端口拖到另一个输入端口建连接（走会话的命令总线，因此可撤销）。

**缺什么**——三处，一环扣一环：

1. **生产代码里没有任何地方构造 `EvalContext`。** 它需要 `(catalog, 端口注册表, INodeEvaluator*, cache,
   faults)`，而没人组装。
2. **`INodeEvaluator` 的实现全在测试里**（`CountingEvaluator`、`RaisingEvaluator`、`MisdeclaringEvaluator`），
   `plugins/` 里一个都没有——插件目前无法提供节点的计算实现。
3. **`NodeDesc::has_compute` 声明了、全仓库从未写过也从未读过。** 也就是说"这个节点类型有计算实现"这件事
   目前无法表达，连承载 evaluator 的入口都还没有。

**最实际的表现**：把输出端拖到另一个节点的参数输入端，**那个连接对 `Run` 不起作用**。`Run` 走
`GraphRun` → `IStateOperator` 这条时间步进的路，`MechanicsBinder` 用 `node.param(...)` 直接读节点自己的
参数，从不看入边。这不是"忘了接"：`execution.hpp` 的文件头专门论证过为什么步进不能是节点（缓存的键要求
纯函数，而时间步进是隐藏状态的定义），所以这是**两套机制的桥**还没写，不是一处遗漏。

**为什么现在不做**：框架阶段的目标是"内容仍然留到以后，只用测试夹具"，而这个桥的全部收益都要等第一个
**有计算实现的模型插件**出现才兑现——目前没有真实消费者。

**重新开启的条件**：写 `plugins/models` 的时候（§9.1）。它会在同一次改动里带出三件事：（1）在 `host` 或
`views/model` 加一个通用 `INodeEvaluator`，按 `NodeDesc::source` 找到贡献该类型的插件所提供的计算实现，
并把 `has_compute` 真正填上；（2）在 `views/model` 组装 `EvalContext` 并让 `Run` 先求值一次；
（3）**之后**才轮到让 binder 尊重入边——把参数来源从 `node.param(p)` 改成"先看入边、再看参数"。
第（3）步必须在（1）（2）之后，否则会让运行期的状态推进去依赖图求值，把两条刻意分开的路缠在一起。

**条件到了一半，而剩下那一半不该做——这是本节的更新。** `plugins/models` 写完了（三个模型 + binder），
而**桥没有被建，也不需要建**：那三个模型的参数是**设置**（一个频率、一个长度、一个阻力系数），不是**算出来的
输入**，所以「先看入边、再看参数」对它们没有任何作用——一条边接进「角频率」端口时，唯一诚实的回应是
「这个模型不接受这个输入」，而不是去求值一个它并不需要的上游。于是第（1）（2）步仍然没有消费者，而
`NodeDesc::has_compute` **保持为假**：一个声明了却没人写的字段，比一个写了却没人读的字段更容易被发现。

**换了一个方向重新开启**：需要它的是**参数算出来的模型**——例如「弹簧常数由另一个节点算出」「质量是上游
拟合的结果」。那时第（1）（2）步一次到位，而且会立刻有一个真实消费者去检验那个接口的形状。现在的状态是
`views/model` 的 `INodeEvaluator` 只存在于测试夹具里，这一条不缩短，只是说清楚了**谁会来缩短它**。

### 9.10 粒子域的执行路径：一个声明了很久的契约终于有了消费者

**这一节记的是本仓库反复出现的那个形状，第三次。** `core/graph/kernels` 有一份完整的契约：`IBatchAdvancer`、`BatchView`、`ParamBlock`、
`AdvanceContext`、`ClampPolicy`、`KernelRegistry`——而在本轮之前，**全仓库没有任何生产代码调用过它们中的任何一个**。
`KernelRegistry` 只在它自己的用例和宜例插件里出现过；没有任何东西构造过 `BatchView`，也没有任何东西驱动过一步。

**缺的不是物理，是两层之间的一模一样。** `graph/domain` 决定**哪些**节点属于粒子域、以什么顺序执行（`DomainPlan::order`），然后就停了。
从那份计划到一个真正步进的循环之间缺一个东西：把每个操作绑到它的内核、参数块与**场槽位**，并在数据上驱动它。

**新模块 `core/graph/particles`，两个东西，都不是物理。**

  - `ParticleState`——粒子批次住在哪里。四个槽位（位置 / 速度 / 荷质比 / 状态），每个槽位都有自己的量纲描述。
  - `ParticleExecutor`——准备一次、每步推进一次、对内核写的每个分量套用钳位策略并计数。

**四个槽位而不是一个数组，而且这不是绕过 field 词汇。** `abi::LatticeDesc` 携带 `dimension`，正是为了让一块缓冲区能说出自己装的是什么；
一个合并的七分量数组说不出来——那不是一个场，是一个 struct，而 `field::is_valid_field`
就会在回答一个没人问过的问题。

**四个槽位全部是 f64，而这是平台所有者拍的。** field 模块的默认是 f32（ADR-0005：场数据走热路径），而粒子批次正是那个默认没覆盖的情形：Boris 推子累积几十万步，
而判定它是否仍在积分正确方程的守恒检查，是两个量级为 1 的数之差。在 f32 里这个差和舍入同阶，
“能量守恒”与“能量漂移等于舍入”就无法区分。

**三个新增的断言，每个都对应一种“循环可能静默错掉”的方式。**

1. **槽位顺序**：一个把索引 2 当成荷质比的内核，会从状态码算出一个看上去合理的加速度，
   用一个把读到的数写进结果的探针内核把它测出来。
2. **就地与非就地**：非就地内核一边读 `in` 一边写 `out`，把同一组槽位交给它会让答案取决于内核内部读写的先后，
   用一个**对顺序敏感**的级联内核跑两遍对比。
3. **钳位**：NaN 对任何上下界都比较为假，所以写成 `if (v > limit) v = limit;` 的钳位会把它放过去；
   用一个写 NaN 与两个方向的无穷的内核，把计数与退役都测出来——并且测出了 `apply` 把 `-inf` 钳到的是**带符号的**下界。

**对粒子而言，“不在了”有三种，而报告不能把它们合并。** `Status` 因此有三个值：被地球吸收是一个降雨事件，逃出模拟区域是一个边界条件，而运算变成非数是第三件事。它们都是“不再推进”，
而一个合并的状态会让报告说不出发生了哪一件——
和把未知不确定度报成零是同一个错。

### 9.11 场与粒子真的接上了：批次布局、12 个槽位，以及一个 2209 倍的错误

**这一轮做的是地磁场套件的第二层：把「一个场模型」变成「一个内核真的读到了它」。** 新目录里两个文件——
`baked_field`（场烘焙成一张均匀格点表，三线性插值读回）与 `boris`（相对论 Boris 推进器，作为粒子域内核）。
而真正值得记下来的不是这两份实现，是接通它们时暴露出来的四件事。

**一、批次布局是两个模块必须同意的一件事，所以它只能被声明一次。** `IBatchAdvancer::advance` 只收到一个
`BatchView`——这是刻意的：契约是「每步一次虚调用、不许每粒子回调宿主」，所以没有第二个参数可以把绑定的场递进去。
于是场槽位**追加在状态后面**：批次固定 7 个槽位（位置 / 速度 / 荷质比 / 状态，然后按 `SlotName` 顺序是 magnetic /
electric / drag）。布局声明在 `core/graph/particles` 的 `BatchSlot` 里，并且用 `static_assert` 与
`ParticleState::Slot`、`SlotName` 两两对齐——**没说出口的约定，就是下一次编辑会改错的那一个。**

**二、没绑定不等于数组变短。** 未绑定的场槽位仍然存在，只是它的 `FieldValue` 不可读。这条不是审美：
如果内核把数组长度理解成「绑了几个场」，那么第一次有人接上 drag 时，它就会把阻力系数当成磁场读，
而算出来的东西仍然像物理。**「没有电场」与「电场恒为零」是同一个力、两件不同的实验**，只有 view 能说出区别。

**三、`PlanRefusal::slot_unbound` 终于被产生了，而知道该拒谁的不是执行器。** 「Boris 推进器离不开磁场」
这条知识只住在一个地方，而执行器**不可能**知道：`IBatchAdvancer` 没有任何方法回答它，加一个就等于把
粒子域的词汇塞进内核契约。知道的是**装配这份计划的人**——它实例化了内核、读了它文档里的槽位表、把一个场节点接到它上面。
所以 `StepPlan::required_slots` 是那个声明，而 `prepare` 据此拒绝。它拒绝的失败是安静的那种：
没有磁场的推进器把场当成零，粒子走直线，运行正常结束，图是错的，而没有任何东西说得出为什么。

**四、`ParamBlock` 从 8 个 double 槽位放宽到 12 个。** 原因是 `field::FieldValue` 描述的是格点的**计数**，
而不是格点**在哪里**：一个要做插值的内核必须被告知网格原点与间距，六个数字。四个标量加六个数字是十。
头文件里那句话本来就是这么写的——「按平台所载最宽的方案定尺寸」——而**这就是那个方案**。
另一条路是在 `core/graph/field` 里加一个携带物理几何的类型，而那个模块存在的理由恰恰是它对物理没有意见。

**五、一个 2209 倍的错误，是被「积分」找出来的，不是被「检查换算」找出来的。** `normalized_charge_mass`
的前两版都把 `(q/m) * B_eq * (R_E/c)` 算成了 `(q/m) * B_eq / (R_E/c)`——**同一个 2209 倍的错误写了两遍**，
第二遍还带着一句「已经修好了」的注释。它活下来的方式是教科书式的：那条本应抓住它的断言写成了
`q_prime / kNormalizedPerSecond == q B / m`，也就是把换算写反了，于是**用例与缺陷互相印证**。
真正的推导只能从运动方程来：`du/dtau = q_prime (E + u x B)` 对上 `d(gamma v)/dt = (q/m)(E + v x B)`，
逐项配平给出 `q_prime = (q/m) B_eq T`，对质子是 **60.546**（`qB/m = 2845.75 rad/s` 乘以光穿越时间 21.3 ms）。
抓住它的是 `magnetosphere.boris.a_uniform_field_gives_the_relativistic_gyrofrequency`：
把一个质子放进 29.7 nT 的均匀场里积分，量它每单位时间转过多少角度——这条用例与它检查的那个换算**不共享一行代码**。
这条经验与测试文件开头那句是同一句：**与代码同一个理解写出来的测试，无论代码做什么都会同意代码。**

**六、`is_time_reversible()` 是 `false`，而且理由是量出来的。** Boris 的速度那一半精确可逆：绕 `B` 转 `theta`
被 `-theta` 转回来，在精确算术里就是单位矩阵。**位置那一半不是**：Boris 用**旋转之后**的速度推位置，
于是前进腿走 `R(theta) v dt`、后退腿走 `v dt`，往返差 `(R(theta) - I) v dt`，量级是 `|v| theta dt`——
**一个步长，不是舍入**。用例在两个步长上各测一次，比值 4 说明它是二阶的。
`schema` 里那个字段第一次被填上 `false` 并不是小事：`kernel.hpp` 自己写着「这个声明之所以值得有，
是因为背后的数字来自一次运行」，而**第一版这里写的是 `true`**。

**七、次步判据的方向，第一版注释写反了。** 参考实现按 `omega_c dt > 0.5` 分步，其中 `omega_c` 是非相对论迴旋频率。
它**高估**了两次：相对论粒子转过的角是 `omega_c dt / gamma`（它没有除 `gamma`），而方案实际转过的角是
`2 atan(|t|)`，对任何 `|t| > 0` 都**小于** `2|t|`。两处同向，所以参考实现**分得比需要的多**——
安全，而且恰好在最热的粒子上最贵。用例把同一场里的冷、热两个粒子放在同一批里，数出本实现取 4 个子步、
参考式判据会取 6 个。

**八、一个下溢到整数转换的 NaN。** 网格索引算术写成 `f < 0 ? 0 : (f > last ? last : f)` 时，
非数的 `f` 对两个比较都为假，于是**穿过两条分支**到达 `static_cast<std::uint32_t>`——那是未定义行为，不是一个错数。
粒子位置在一次发散的子步里真的会变成无穷，所以这条路径不是假想的。改成两个取反的比较之后，非数落进第一条分支。

**数字**：`tests/unit/plugins/test_magnetosphere.cpp` 22 个用例 / 597 条断言（上一轮 12 / 105），其中六个驱动
推进器的用例**走完整的桥**：`ParticleState` + `BakedField` + `StepPlan`（场绑定、`required_slots` 声明）+
`ParticleExecutor`。唯一不走执行器的是 `a_bad_batch_is_refused`——**拒绝必须在边界上查，而不是通过那个本该
阻止它的代码去查**。`tests/unit/graph/test_particles.cpp` 14 / 299。

### 9.12 场域真的跑起来了：`field_handle` 的发布者、第一个生产 `INodeEvaluator`，以及一条边就是一次绑定

**这一轮把「一个场模型」变成「图里的一个节点」，并且让它真的接到粒子上。** 三样东西：`core/graph/field`
的 `FieldSet`、`plugins/magnetosphere` 的 `field.dipole` 节点与 `DipoleEvaluator`、以及把两者接到
`StepPlan` 上的 `build_particle_plan`。而最值得记下来的，是接通它们时暴露出来的六件事。

**一、`field_handle` 一直缺一个发布者，而这不是修辞。** `ports::Value` 的 `field_handle` 只携带一个
`abi::LatticeDesc`，头文件写得很清楚：数据由「`core/abi` 里的发布者」保证存活。**在这个仓库的整个历史上，
那个发布者不存在。** handle 能穿过 JSON 格式往返，端口类型注册表能区分向量场与标量场，而没有任何东西能把一个
handle 变成样本。于是有了 `FieldSet`：它拥有已发布的样本缓冲区，键是**谁发布的**（节点槽位 + 输出端口）。

**键为什么不是那个描述符。** 用 `LatticeDesc` 做键看起来很省事——handle 里本来就有——而且错了：两个恰好烘焙出
同样形状格点的节点会共享一个条目，第二次烘焙会覆盖第一次，于是一张有两个不同倾角偶极子的图会跑两遍其中之一。
一个已烘焙场的身份是**哪个节点产生了它**，这正是计划知道的事。同理，键是两个整数而不是 `graph::NodeId`：
本模块依赖 `abi` 而不知道节点与边是什么，一个必须知道 NodeId 是什么的存储，没法被一个手上没有图的烘焙器使用。

**二、`INodeEvaluator` 同样一直没有生产实现——这是同一个形状的第四次。** `core/graph/eval` 有一份完整契约
（`INodeEvaluator`、`EvalContext`、`EvalCache`、`evaluate_graph`），而全仓库唯一的实现是
`tests/unit/graph/test_eval.cpp` 里三个桩。这一轮的本套件成了场域的**第一个真实消费者**，正如上一轮它成了
粒子域的第一个真实消费者。

**而这一次接通暴露出一条契约细节，值得单独记：`evaluate_graph` 对图里每一个节点都调用求值器**，不管它属于哪个域。
那些桩的做法是对不认识的类型返回 `unknown_node`，而如果照抄，**任何含推进器节点的图都将无法烘焙**——而且报的会是
「没有人实现这个类型」，可这个类型明明注册过。所以规则改成：`FieldNodes::node_types()` 里的是我的、要烘焙；
其余的**产出为空**。一个没人实现的节点类型是 **validate** 的发现（加载时报告未知类型），不是烘焙失败。
把这条量出来的是 `nodes_visited == 2 && nodes_computed == 2`：推进器真的到达了求值器，求值器为它产出了零个值并成功返回。

**三、一条边就是一次绑定，而这不需要任何新概念。** 场通过**边**到达推进器，边落在哪个端口**就是**哪个槽位：

    field.dipole:1 --线--> particle.boris:1   即   SlotName::magnetic
    field.dipole:1 --线--> particle.boris:2   即   SlotName::electric
    <标量场>       --线--> particle.boris:3   即   SlotName::drag

这正是 `StepPlan::fields` 按 `SlotName` 索引而不是按端口号索引的原因：推进器的端口布局给一条线赋予含义，而那个布局
只在 `PusherNodes::node_types` 里声明一次。用户把偶极子接到阻力插座上，会被**端口类型**拦住
（`kVectorField` 进 `kScalarField`），而类型错误本来就该在那一层报。

**四、网格归属节点，于是端口号必须只写一遍。** 一个烘焙场是「模型在格点上求值一次」，所以拥有模型的节点也必须拥有格点。
代价是一份**两个读者**必须同意的小契约：求值器**从输入值**里读网格来烘焙，计划构建器**从节点**里读同一个网格来填内核的
六个网格参数槽。两个读者就是两次分歧的机会，所以端口号是这一处的常量，`FieldNodes::read_from` 是唯一的读者，
两边都调它。这条与内核参数索引的规则是同一个，理由也是同一个：它防止的失败是**内核采样了一个不在样本所在处的盒子**——
两边各自都对，合起来是错的，而没有哪个半边自己的测试能发现。

**五、构建器不预先检查「有没有接磁场」。** 一条还没接的线是画图过程中的正常状态，而不是构建器能报的错；
内核也报不了——它拿到的是一个批次，而**缺失的场与恒为零的场在一步之内完全一样**。能报的是这一步自己的声明：
`StepPlan::required_slots` 带着 `BorisAdvancer::kRequiredFields`，`ParticleExecutor::prepare` 据此以
`slot_unbound` 拒绝。上一轮为了这个枚举值加的机制，这一轮第一次被**生产代码**产生出来。

**六、端到端那一条用例测的是一个「符号」。** 图里一个偶极子、一个质子，烘焙、构建、执行 2000 步，然后断言速度在
`xy` 平面里扫过的角是**逆时针**的。这个预测没有任何半边能单独做出：偶极子的符号约定（赤道处 `B` 指向南，`B_z < 0`）
与推进器的旋转方向必须一致，任何一边翻了，粒子都会绕着一个**仍然指向南**的场朝反方向转。而频率不能拿起点处的场来预测：
回旋中心离起点一个回旋半径，在 `1/r^3` 的场上那是 2.2% 的差别——**这条用例的第一版就差了 2.7%**，
所以它改成从**引导中心**处的场算，一阶变化在一圈上互相抵消，剩下的是 `(rho/R)^2` 量级的 2e-4，
容差 1% 因此是有依据的而不是宽松的。

**数字**：`tests/unit/plugins/test_magnetosphere_nodes.cpp` 10 个用例（新文件，与原来的 22 个同属一个测试二进制）；
`tests/unit/graph/test_field.cpp` 从 13 个增到 17 个（`FieldSet` 的四条）。`field.dipole` 默认 17 节点/轴、
一地球半径一格，八个地球半径见方——学生放下节点就能跑。

### 9.13 一个图变成一次运行：发射器、状态通道，以及一个「流角」把自己转没了的教训

**这一轮把套件从「五个各自能跑的一半」变成一个整体：图进，实验出。** 新东西三样：`particle.ring_emitter`
节点、`particle.boris` 的**状态通道**（进/出各一个端口），以及 `MagnetosphereRun`。而最值得记下来的是五件事。

**一、`has_compute` 不是「烘焙会为它产出一个端口值」，而是「这个节点有实现」。** 发射器与推进器的产物都是
`ParticleState`，不是端口值，所以第一版把它们写成 `has_compute = false`——而 `graph/domain` 的 `build_plan`
**只把 `has_compute` 的节点放进域计划**，于是三处用例全报 `empty_plan`，报的还是一张完整正确的图。
这条契约细节值得单独记：那个标志的读者是**域层**，它问的是「这个节点有没有实现」，不是「求值器会不会为它产出值」。
发射器的实现是**运行**，推进器的实现是**内核**。

**二、状态通道：端口类型是 `kParticleBuffer`，而没有值从上面过。** 粒子域的产物是 `ParticleState`，
它在执行器里、太大、也不是任何一种 `ports::Value`。这个端口存在的理由是**线可以被画出来、被类型检查、被域层的可达性遍历看见**，
并且让运行能**问图**「哪个发射器喂这个推进器」，而不是在某处找一个发射器类型的节点。这与平台对「声明输出」的既有决定是同一条：
拓扑是数据，而线上跑的不一定是值。

**三、发射器为什么要走到图里去回溯。** 一个运行必须回答「这个推进器推进的是哪些粒子」，而只有一种答案是图的事实而不是计划顺序的巧合：
沿状态线**向后走**。找类型会在一张有两个发射器的图里静默挑一个，取粒子域顺序里第一个则取决于拓扑并列时的槽位序。
回溯还得是循环而不是一跳，因为一个计划里可以有几个串联的推进器。而两个发射器喂两条链，是「一个状态缓冲区」回答不了的问题，
所以它被**按名字拒绝**（`several_emitters`）而不是随便选一个——那正是「一个文档里放两组实验」会产生的图。

**四、一个把「流角」绑在粒子方位角上的教训。** 发射器的第一版让每个粒子的**速度垂直分量**沿它自己的方位角转，
理由听起来很自然：环上每个粒子朝不同方向。实际算下来，垂直基 `(p̂₁, p̂₂)` 是**随位置旋转**的（`p̂₁` 是径向在垂直面里的投影），
所以「流角 = 方位角」把旋转**精确抵消**掉了——十二个粒子的速度全部平行，得到的是一个**平移的环**，不是回旋的环电流。
抓住它的是一条断言：相邻粒子速度之间的夹角本该是 30 度，实测 0。修法不是调参数而是**换概念**：把「相位散布」拆成
`flow_angle_deg`（整个族群在垂直面里朝哪，90 度 = 环电流，0 度 = 径向流出）与 `ring_span_deg`（位置铺开多少圈），
于是「流角」是族群的一个数，而不是粒子位置的一个函数。附带一条：那条「速度垂直于自己的半径」的断言只在**无倾角**的场里成立——
有倾角时局部场不垂直于半径，那句话就变成了关于场自己框架的陈述；用例因此把族群断言放在无倾角的场里测，把倾角场留给「俯仰角是相对**局部**场量的」那条。

**五、一份采样器，两个调用者。** 发射器要知道局部场方向才能按俯仰角发射，于是它成了三线性插值的第二个调用者。
原来的插值住在 `boris.cpp` 里，第二份拷贝会是「两个节点之间场是多少」的两个答案，而不一致会表现为**粒子从发射处开始就以略微不同的曲率飞行**——
哪一半自己的测试都发现不了。所以插值被提到 `baked_field.cpp`（`sample_baked` / `sample_baked_scalar`），
`BakedField::sample` 变成它的薄包装，一条用例把两者**逐位相同**钉住，另一条用例测 `f32` 分派这条真实的支路（ADR-0005 让场默认 f32）。
「一个采样器、两个调用者」这条不只写在注释里：`sample_baked` 同时读 f32 与 f64，而 `BakedField` 只会产出 f64，
所以 f32 的那条分支只有在自由函数里才可能被测到。

**数字**：`tests/unit/plugins/test_magnetosphere_run.cpp` 5 个用例（新文件），套件合计 38 用例 / 3857 断言；
`MagnetosphereRun` 把「图 → 计划 → 烘焙 → 发射 → 绑定 → 准备 → 步进」串成一条线，并让 `slot_unbound`
在**完整的图**上被产生出来（推进器的磁场插座不接线时）。

### 9.14 套件从调色板到「按下运行」之间：一次诚实的挂载与一句被改写的话

**第四轮结束时套件的四层都通了，而它仍然只有测试夹具能到达。** 这一轮做的是把那个洞补到**能补的那一半**，
并且把补不上的那一半说清楚。

**一、应用挂载了套件的三个节点类型。** `views/app/main.cpp` 现在通过 `content_host` 挂载
`field.dipole` / `particle.ring_emitter` / `particle.boris`，与仪器、格式、实验包走同一条路（都在
`add_builtin_node_type` 的账本里，所以 `origin_of` 答得出、会话收得回）。**在这之前，这三个类型只有用例注册过**
——而 `docs/plan-tree.md` §9.9 把这种形状点了名：「只有测试夹具能到达的能力位，看起来每一项检查都是绿的」。
挂载之后用户能做的是真的事：放下一个偶极子、把一个环发射器和一个 Boris 推进器接上去、调俯仰角与 L 壳、保存文档。

**二、而按下运行之后会看到什么，这一轮也管了。** 粒子域的产物是 `ParticleState`，它由套件自己的
`MagnetosphereRun` 驱动；`views/model` 的运行控制器驱动的是 `IStateOperator` 与它自己的 `StateView`。
那条路没写，而**一个写得不好的拒绝语比没有拒绝语更糟**：原来的句子是「no node in this graph has an operator yet」，
对一张节点类型**已经注册、线也已经接好**的图来说，它会把读者送到「哪个插件没装」上去。
所以 `graph/execution::check_run` 现在会**先看一眼那个节点属于哪个域**：

  - 粒子域（`allow_in_particle_domain && !allow_in_field_domain && has_compute`）→ 说出节点类型，
    并说清它的状态是**粒子批次**而不是这个循环的 `StateView`；
  - 场域（反之）→ 说出节点类型，并说清它是要**烘焙**的，不是要运行的；
  - 既没有 `has_compute` 的 → 保留原来那句，因为「这个节点没有实现」是另一件事（一个还没写完的调色板条目，
    或者一个只做声明的 render 节点），给它按域命名会把读者送到一个从来不是问题的地方去。

两个域分开说，是因为接下来要做的事不同：场节点要先烘焙，粒子节点要先发射。

**三、这一轮明确不做的是什么，以及它的重新开启条件。** 视图层的粒子域运行路径（把
`MagnetosphereRun` 接进运行控制器：先烘焙场域、再按发射器建状态、再驱动）是一件**属于平台**的事——
它服务的是任何粒子套件，不是这一个——所以它没有被塞进套件里。重新开启条件写在 `views/CMakeLists.txt`
与 `main.cpp` 的注释里，与代码放在一起，而不是只写在文档里：**当第二个粒子套件出现时**，
说明这条路径是一个平台能力而不是一个套件的私事，那时它该被抽出来。

**数字**：`execution.check_run.names_a_node_of_another_domain` 一条新用例（`test_execution.cpp` 16 用例 / 461 断言）；
GCC 791、MSVC 793 全绿。**方言门禁自检的偶发失败：已观察到两次**，两次都出现在 **GCC** 那半、两次都是 **自检**（不是门禁本身）、两次单独重跑门禁与自检都通过。它不再是「一次未能复现」，因此值得一次专门的排查而不是再记一笔——下一次出现时应该先把 `Testing/Temporary/LastTest.log` 里那一段抄下来再重跑，否则证据又会被覆盖。第一次出现在跑完整矩阵时
`meta.dialect_checker`（方言门禁的**自检**，不是门禁本身）报失败，而单独重跑门禁、自检、
以及随后的整套矩阵都通过；记录在此以免下次又被当成新问题。

### 9.15 整张图的一次运行：内容自己提供运行，视图层不认得任何套件

**`GraphRun` 是平台的运行循环，而它是「一个算子绑在一个节点上」。** 这覆盖了所有「每粒子状态是几个 double」的域，
但覆盖不了一次**启动本身是计算**的运行：地磁场图要先**烘焙**（场域求值到格点上，可以分配、可以阻塞）、
再**发射**（一个发射器节点展开成粒子批次）、然后才谈得上步进——而这三段没有一段是 `GraphRun` 能被告知的。
知道怎么做的是**内容**，所以视图层不能点名它；内容也不能点名视图层。

于是 `IGraphRunProvider` / `IGraphRun`，比 `IOperatorBinder` 高一层、倒置方式相同：接口住在主题是它的模块
（运行循环契约），实现住在知道怎么做的插件里，而**应用**是唯一知道这个 build 有哪些插件的地方，
因此也是唯一填列表的地方。

三个决定值得写下来：

  - **接口不提到任何场类型。** 提供者拥有它运行所需的一切（包括烘焙好的存储），交回来的是报告与位置快照。
    这是这个头文件能住在一个不懂场的模块里的原因，而它有代价：**想画场本身的视图没法向它要**
    （磁力线、色图）。重新开启条件是一条 render 声明说「画节点 X 的场」——那时存储从某个套件的私事变成契约的一部分。
  - **拒绝是提供者自己写的一句话**，不是错误码。构建拒绝的理由是提供者自己的、而用户对它们的动作各不相同：
    磁场插座没人接、接了一个从没烘焙过的场、两个发射器喂两条链。`diag::ErrorCode` 里没有这些名字，
    压成一个码就把读者唯一能用的那部分扔掉了——与 `PlanRefusal`、`RunRefusal` 同一条理由。
  - **`positions()` 是快照不是轨迹。** 轨迹是调用方连着取快照，那是视图的决定；一个把每个粒子每一步都攒下来的运行
    会持有 steps × particles × 3 个 double，而调用方可能只要最后一帧。

`MagnetosphereRun` 实现 `IGraphRun`；`build_with_own_fields` 让它自己烘焙场域——提供者没有可借的存储，
这正是接口能不提到场类型的原因。提供者为每个推进器合成一条声明输出：**在一张粒子图上按下运行，
意思就是「跑里面的推进器」**，而一个声明输出编辑器是将来会替换掉这行合成的东西。

**还没接的一环，以及它为什么不能半做。** `views/model` 的运行控制器还不会去问一个提供者列表，
所以应用里没有任何东西调用这个接口。一个只挂在列表上、没有任何调用者的挂载点比没有更糟——
它看起来像接通了。这一段留给下一轮一次做完：提供者列表、控制器的第二条路径、应用挂载，加用例。

### 9.16 一个潜在的链接错误，以及它是怎么活过一整轮的

**这一节记的是一个流程缺陷，不是设计缺陷，而它值一节。** 给运行控制器加「第二条路径」的那一轮，
`run_providers` / `mount_run_provider` / `clear_run_providers` 三个函数的定义被脚本写进
`views/model/execution_binders.cpp`，脚本报了一句 "patched"——**而它们从来没有落进那个文件**。
于是提交里 `run_controller.cpp` 引用了一个全树不存在的符号。

**它活过一整轮，是因为我验证的东西不对。** 那一轮我构建了两个目标：`qp_views_model`（**静态库，归档不解析符号**）
与 `qp_test_views_model`（它根本不拉 `run_controller.cpp`）。两者都绿，于是我以为改好了。
第一个真正链接并使用运行控制器的目标 `qp_test_run_controller` 一构就报 undefined reference。

**两条规矩，从那一轮起。** 第一，**验证一个改动，要构建会真正使用它的可执行文件**——库的「构建通过」不等于任何东西。
第二，**脚本打印的成功信息不是证据**：`patched` 只说明脚本走到了那一行，不说明写进去的内容在文件里。
修完之后，我是用 `qp_test_run_controller` **链接通过**来收尾的。

修法本身很小：把三个定义放进真正被编译的那个文件，与 binders 并排——两份头文件本来就被同一个调用者在
同一时刻填，拆成第二个翻译单元会把一件事看成两件。`mount_run_provider` 照 `mount_execution_binder` 的做法去重。

**紧接着补上的是那条一直没有的用例**（`views.binders.a_provider_runs_a_graph_the_operators_declined`）：
一张算子本会认领的图、**不给 binders**，没挂提供者时得到算子循环自己那句话，挂上之后得到提供者的报告——
两个用例只差「有没有挂提供者」这一件事。钉子四枚：次序、报告、快照（`particle_positions`，画布以后要读的字段）、
以及拒绝**原样透传**（这一层没有「磁场插座没人接」的词汇）。用例末尾清空并断言列表为空：那是进程级静态，
泄漏会改掉后面每一个用例的答案。

### 9.17 接口放错层：第三次同一类错误，这次在写实现之前抓住

**这一节记的是一个架构错误和它的代价，因为它是本仓库同一类错误的第三次。** 渲染域说渲染节点是**声明**、
`build_plan` 把它放进 `plan.render.declared`，套件也有了 `render.particles`——缺的是另一端：谁来读一条声明。
我把 `IViewItem` / `ViewScene` / `ViewRequest` 写进了 `views/model`。

**下一个要写的东西是一个插件**（把位置快照变成场景），而插件实现这个接口就意味着 `plugins → views`。
这正是 `views/model/execution_binders.hpp` 已经用血记下的那条：`views → plugins → views` 曾经是一个环，
结论是**插件要实现的接口必须住在 `core/`**。我犯的是同一个错，只是方向反过来。

**代价差一点就是"重写"**：一个已提交的头文件、它的 `.cpp`、它的用例分区、两处 CMake 条目。
之所以是"差一点"，因为我在写那个插件之前停下来了——先确认它该住哪，再写。这是本会话里第四次"先查后写"
省下一次拆除（前三次分别是：潜在链接错误、`main.cpp` 漏包含、声明写在用它那行之后）。

**修法**：契约搬进 `core/graph/domain`——它消费的 `DeclaredOutput` 与渲染计划就是那个模块自己的词汇，
依赖集也已经覆盖契约提到的全部东西，不需要放宽任何依赖边；挂载列表跟着搬，与 `build.cpp` 并排；
用例换到 core 分区（契约门禁要求头文件的 `@tests` 在能看见它的那次调用里）。
**接口本身也顺手去掉了对视图层的引用**：第一版 `ViewRequest` 拿着 `const RunResult*`，那是 `views/model`
的类型；改成"位置快照 + 步数"之后，它可以原样搬走——这件事在搬之前一轮就做了。

### 9.18 渲染链条：声明、生产者、绘制者，以及一条被用例抓住的错误规则

四段拼起来：`render.particles`（图的声明）→ `RunResult::render_declared`（生产者）→ `IViewItem::scene`（绘制者）
→ `ViewScene`（一个值：点 + 边界）。三段各有一次"决定"值得记：

  - **声明节点的输出端口永远没有值经过**。声明输出是 `(node, port)` 对，所以不能被声明的节点就不能被要求；
    这个端口是"被画的那个东西"的名字。改成声明推进器的状态端口，就把"画什么"的决定放进了视图而不是图里。
  - **生产者的规则试了两次，用例抓住了第一次**。第一版是"没有 `has_compute` 的节点"，它把所有把那个标志
    留成默认值的类型都扫了进来——示范库的 spring-damper 就是其中之一，于是一张**什么都没有可画的图报告了
    一件要画的东西**。规则改成把渲染域写全：没有 compute **且**既不是烘焙内容也不是步进内容。
  - **绘制者不持状态**，于是**没有拖尾**：拖尾是一串快照而请求只带一张，宿主累积它、渲染节点的 `trail`
    参数约束长度。这一条是接口要求的，不是省事。

**契约门禁的一条规则也在这一轮被记住**：C6「孤儿用例」——未被任何头文件 `@tests` 引用的用例会被拒绝。
渲染声明生产者那条用例第一次没被认领，门禁直接拦下了。

   然后遍历 `qp::graph::view_items()`，对 `draws(type_name)` 为真的项取 `scene(request)`。
   类型名要从图里拿：`decl` 只给 `(node, port)`，所以 `graph.find_node(decl.node)->type_name`。
3. **一次挂载**：`views/app/main.cpp` 里挂 `qp::plugins::magnetosphere::ParticleViewItem`
   （与 node types、run provider 同一段，注意**声明要在使用它那行之前**——MSVC 抓过这个错）。

**验证只能在 MSVC 树上做**：Qt 在 GCC 树里是关的，`main.cpp` 与 `views/qt` 根本不参与那次构建。
所以收尾必须是 `powershell -File scripts\build.ps1`（两棵树都跑），而不是只跑 GCC。

**为什么这里停住**：这一段的每一步都只能由一次约十分钟的 MSVC 构建来验证，而写它需要先读两处现状
（Qt 控件的写法、`views/CMakeLists.txt` 的源列表）。本会话里三次"先写后查"（潜在链接错误、漏包含、
声明顺序）都出了缺陷，所以宁可把它作为一次完整的、有充足上下文的改动来做，也不在这里挤。

### 9.20 求值器怎么拿到它的输入：`field.sum` 与一个契约缺口

**需求排序里的第一项是「组合靠接线」，而它要求框架回答一个此前没被问过的问题。** 一个 `field.sum` 节点读两个场输入，
而它需要的不是输入的**描述符**，是输入的**样本**：`ports::Value` 的 `field_handle` 只带一个 `LatticeDesc`、不带键
（刻意的——值不能携带指向别人生命周期的指针），所以通向样本的唯一道路是存储，而存储按 `(node, port)` 索引。
`INodeEvaluator::evaluate` 拿到的却是自己的 id、自己的描述、以及输入的**值**，没有它们的**来源**。

**两条路，选了一条，理由写在 `set_graph` 的注释里。** 一条是改 `INodeEvaluator` 的签名让它携带每个输入的
`(source node, source port)`——那是对一个 `@frozen yes` 接口的有意修改（本仓库的规矩是这种改动必须被刻意做出并记录）。
另一条是让**求值器借用图**：组合根在开始烘焙时正好有它，而解析一条场输入与计划构建器解析一个插座是同一件事——
沿边走进 `(id, port)`。选了后者，因为它在不改任何冻结接口的前提下把接线读自**拥有接线的那一处**。

**重新开启条件写下来了**：当**第二个**求值器需要图时，它的家是 `EvalContext`——那个对象本来就传给驱动者，
可以携带它而不必让每个求值器各持一个指针。

**`field.sum` 本身**：两个 `kVectorField` 输入都 required（只有一个加数的「和」不是和，静默透传会造出一张看起来
组合过、实际没有的图）；两个格点必须一致，**不一致就拒绝而不是拟合**——拟合会造出两个模型都没产出过的场。
用例逐节点（不是抽样）断言和等于两个加数之和，并断言加数**未被修改**：一个写进输入缓冲区的节点，
会让图里的第二个读者看到第一个读者的算术。

**用例第一版就撞上了那条拒绝**：我把均匀场的格点设成 1 地球半径 17 节点，而偶极子是 0.25 / 65——
烘焙被拒绝，正是拒绝在工作。这一条写进了用例注释，因为它是「两个格点必须一致」这条规则的现场证据。

### 9.21 电场的生产者：同一个表、不同的量纲，以及一棵会撒谎的构建树

**推送器从写下的第一天起就有一个电场插座，而此前没有任何东西为它生产过场。** `PusherNodes` 读两个场插座
（磁场与电场），`Boris` 的半步加速里两者各占一项，而参数表、端口、计划构建器全都齐了——缺的是**生产者**。
这一项补上它：`field.uniform_electric`，均匀电场，单位 V/m，落在与磁场烘焙相同的均匀格点上。它让 `E x B` 漂移
成为可演示的东西（那正是磁层有对流图形的理由），也是课程把跨极盖电场当成均匀场来处理的第一个情形。
默认值取 `1.0e-5` V/m 而不是随便一个数：那大致是映射到赤道面的跨极盖场量级，于是它产生的漂移在一次运行里
看得见，而不是要跑一千次。

**电场表与磁场表是同一个东西，把它们区分开的只有描述里的量纲——而这正是它危险的地方。** 两者都是「均匀格点上的
f64 三元组」，`field_handle` 只带 `LatticeDesc`、不带量纲，推送器通过**同一套词汇**读两个插座。于是把两者搞混的
描述会让电场表现为磁场，而**下游没有任何东西能察觉**：粒子照样积分、图照样收敛、屏幕上照样有轨迹，只是漂移不见了。
这不是假想的坏法——同一个仓库里那个 2209 倍的错误（§9.11）就是这么活过两轮的。所以本项的可观测断言就是量纲本身：

| 场 | M | L | T | I | SI |
|---|---|---|---|---|---|
| 磁场（`tesla_dimension()`） | 1 | 0 | -2 | -1 | kg / (A s^2) |
| 电场（`volt_per_metre_dimension()`） | 1 | 1 | -3 | -1 | kg m / (A s^3) |

四个指数里有两个不同（L 与 T），所以「混了」是一个能被断言的事实，而不是一条注释里的提醒。`bake_uniform` 因此
多收一个 `dimension` 参数，默认仍是 tesla——**每一个既有调用点读到的还是它一直读到的东西**，这是默认值的全部理由，
写在上一个提交里。

**端口编号刻意与均匀磁场节点一一对应。** `e_x/e_y/e_z` 是 1、2、3，格点从 4 起——与均匀磁场节点完全相同。
端口号是**节点类型内部**的编号（§9.14 那次注册被宿主拒绝，是**同一个类型内部**撞号，不是两个类型之间），
所以两个场生产者共用一套编号是安全的，而且有用：`read_from(view, kPortElectricOrigin0)` 的形状与磁场那边一致，
读过磁场节点的读者已经知道电场节点的格点在哪里。这条选择也解释了为什么电场节点的实现只有常量与量纲两处不同。

**`mount` 的期望值第三次迁移（3 → 4），两个测试文件各一行。** 这条断言是「有了一种新类型」在测试里唯一能被观察到
的位置，所以它每次都跟着改：`Scene()` 构造里 `FieldNodes::mount(host)` 从 3 变 4，类型表用例里 `types.size()`
从 3 变 4 并新增 `types[3].type_name == kUniformElectricType`。顺序被断言而不是查表——调色板里出现的顺序就是
用户看到的顺序。

**本轮的电断用例是「扩展一个既有用例」，而不是新增一个，而这件事有可观测的后果。** 断言写进了
`magnetosphere.field_nodes.a_uniform_field_is_uniform`，因为那条用例已经在同一张格点上烘焙了均匀磁场，
而本项的主张恰好是**这一对**：两个描述、一个形状。断言逐点（125 个点，不是抽样）要求每个点的 E 等于设定的三元组，
并要求磁场表的 `L == 0 && T == -2` 就写在电场表的 `L == 1 && T == -3` 旁边。后果是 **ctest 计数一项都没动**：
磁层 44 项注册两侧相同，而 GCC 800 / MSVC 802 里这一项贡献 0。**注册测试数不是特性数**——只盯那条计数的话，
这一轮看起来什么都没做，而它交付的是推送器第二个插座的第一个生产者。

**提交边界没有守住，而且上一个提交的信息说我守住了。** `7a6f94e` 的信息里写着「电场节点本身是下一步，不在这个
提交里：常量、端口与求值器分支是另一步」，而它的 diff 里**常量与端口就在那个提交里**（头文件 21 行：
`kUniformElectricType`、三个 `kPortE*`、`kPortElectricOrigin0`）。真正落在这一步的是求值器分支与用例。
成因是按文件 `git add`，而当时两件事的改动在同一个文件里。**没被发现的原因是它不可能被发现**：那些声明在被
引用之前是惰性的，于是八道门禁、两个编译器、八百项测试全部保持绿色——一个只加了 `static constexpr` 的头文件
没有任何消费者，因而没有产生任何信号。这条值得写下来，因为它量出了「门禁全绿」的边界：**门禁量的是引用，
不是意图**，一个还没有引用的声明在门禁眼里与不存在无法区分。

**本轮还清掉了一棵会撒谎的构建树。** 为了核对计数，我跑了 `ctest --test-dir build-gcc -N`，得到 **564 项、
其中磁层 0 项**——一个可以报告「全部通过」却**完全不包含正在开发的功能**的构建树。它比现在的命名早了一代：
GCC 树是 `build/`，Qt 树是 `build-msvc`，而 `build-views` / `build-release` 是 `package.ps1` 与 README 用的
名字。仓库里对 `build-gcc` 的**引用数为 0**：没有脚本、没有门禁、没有文档提到它。它不是「旧的但有用」，
而是一件能产生假绿的本机产物，所以删掉了（重建是一条 cmake 命令）。实测的两棵树差异是干净的：`build` 800 项、
`build-msvc` 802 项，差的 2 项正好是 `qp_test_views_qt.all` 与 `qp_test_views_theme.all`——Qt 只有 MSVC x64
套件，GCC 树里 Qt 是关的，那两个二进制项在那棵树里根本不存在；磁层在两个树里都是 44 项。这次它吃掉了一轮诊断，
记下来的理由是：**「哪个目录是权威的」必须能从仓库里读出来，而不是从记忆里。**

### 9.22 磁场线：第二个视图项逼出来的三个契约，以及一次真的画到屏幕上的检查

**需求排序里的第二项是「磁场线」，而它的价值不只在图上：它是第一个「声明里点名了一个烘焙产物」的渲染节点。**
`render.particles` 说「画这些粒子」，`render.field_lines` 说「画这条线上的场」——后者要求读**样本**，而在此项之前
没有任何接口能把样本交给视图项。`run_provider.hpp` 早就把这个代价写在注释里（「想自己画场的视图无法向本接口索取
它」），并把重新开启条件写成一句话：**一个声明「画节点 X 的场」的渲染域**。这一项就是那个条件被满足：`IGraphRun::fields()`
是付款，而那段注释改成了「条件已触发」。同一轮里 `view_items.hpp` 的第二个条件也触发了（「当第二个视图项存在时」），
但**没有**建注册表——理由写在下面第 3 条。

**一、追踪器：五条停止原因，以及两处不能照抄的地方。** 移植自参考实现 Geopack `TRACE_08` 的 `STEP_08`：五级
Runge-Kutta-Merson，`err = Σ|R1 − 4.5R3 + 4R4 − 0.5R5|`，误差超限减半、小于容差 4% 时增长到步长上限。放进
`plugins/magnetosphere/trace.*` 而不是 `core/`，判据与积分器同一条：`core/graph/kernels` 自己写着「一个积分器都没有」，
曲线怎么找是一个带容差的方法，是内容。两处**读懂了就不能照抄**：

  - **场为零时必须停下。** 参考实现里零场让每一级都是零，误差估计因此是零，步长一路涨到上限而位置不动，循环一直
    追加重复点直到点数预算耗尽。这里它是 `no_field`。
  - **命中地面的点要解出来，不能插值。** 参考实现在弦上做线性插值，落点半径是 `0.9999874883` 而地表是 `1.0`——这是
    在 L = 5 那条线上**实测**的数字，因为弦上的半径对弦参数是二次的而不是线性的。解一次二次方程只花一次开方、每条线
    只做一次，换来的是「落点在地表上」可以断言成等式而不是容差。

**二、两个判据是被用例逼出来的，而不是设计出来的。** 闭合检测有两套，因为一套不够：**圆形**场线的半径恒定，径向
反转计数器结构上看不见它闭合；而在同一条线上 `dr` 是两个几乎相等数之差、符号是舍入噪声，没有死区的计数器会在第五步
就以错误的理由宣告闭合（死区取步长的千分之一，比任何真实的径向转折低三个数量级）。第二处更值得记，因为它是这一轮
**几乎发出去的**错误：`x + (k1 + 4k4 + k5)/6` 里**只有 k1 被朝向化**时，实际推进量是 `((sense+5)/6)·unit_B`——
前向那一半方向正确、步长少三分之一，后向那一半**沿着场走而不是逆着场走**。实测：一步走 0.133 而不是 0.2，停在距
种子 0.13 处、与前向同一半球。四个用例同时失败，这是好套件该有的形状。

**三、宿主改成「每个视图项一块面板」，而槽位注册表**没有**因此出现。** `view_items.hpp` 当年写的条件是「当第二个
视图项存在（磁场线、纯拖尾视图）时抽注册表」——条件满足了，注册表仍然不在，理由记在文件里：宿主给**每个挂载的项
一块自己的面板**，「这一项画进哪个槽」仍然只有一个答案，由项的身份决定而不是由它声明。真正变的是宿主：它不再按
控件类型找面板，而是遍历 `view_items()`、把每条声明交给每一项、并为每一项留一块画布。注册表的重新开启条件因此
被改写成更锐利的一句：**当某项需要「选择」时**（两项争一块面板、一项画进两块、或图里出现同类型的两个项）。

**四、只有场的图也能运行。** 一张「偶极子 + 磁场线渲染项」、一个粒子都没有的图，是这套工具能画的最简单的画，
而它此前被 `no_pusher` 拒绝。烘焙本来就是对**整张图**求值，缺的只是「允许在那里停下」：`build_with_own_fields`
现在在图里没有推送器时直接成功，并让三处各自说明自己的意思——`advance` 什么都不做并说得出为什么，`report` 报零
人口普查外加一句话而不是空报告，`built()` 为真。替代方案是再造一套「只烘焙不运行」的机制，而那正是这套套件存在的
理由所要避免的烘焙/运行二分。

**五、画面上真的检查了一次，而它抓到的东西比功能本身多。** 用一份手写的 `.qpd`（偶极子 → 磁场线）打开窗口、按
运行，得到四件事：

  - **`main.cpp` 的挂载计数在骗人。** 控制台写着 `magnetosphere: mounted 6 of 3 node types`：那个字面量 3 是
    **加电场的节点之前**写的，而它是把三个计数**相加**后与一个字面量比较。一个描述别的模块清单的数字住在这一边，
    与仓库里反复出现的过期期望是同一个形状。改成每个计数各自比较。
  - **右栏装不下六个 dock，而 Qt 不会滚动。** 组件把多出来的 dock 压成**零高度**：诊断打印出五个
    `visible=0 size=100x30`，而窗口看起来完全正常、每一项检查都通过。这是「截图不能替代提问」的最好例子——第一次
    尝试（都堆在右栏）与第二次（右栏内互相成标签页）分别失败于「看不见」和「看得见但只有二十像素高」，而
    `tabifyDockWidget` 对刚加进同一区域的 dock 干脆没有生效（标签栏只有一个标签，第二个 dock 保持未布局的
    100x30）。最终形状是一句不可能半生效的规则：**N 个项、N 块面板、在窗口底部并排**，实测各 638x213。
  - **窗口默认比屏幕宽。** `resize(1280, 720)` 在本机 144% 缩放下要 1843x1037 物理像素，而显示器是 1707x1067：
    右边那 95 逻辑像素里装的正是右栏——读数、置信度、图像面板，也就是说窗口一开就把自己的右边缘开到了屏幕外。现在
    默认尺寸被可用屏幕几何限制。
  - **`Fit` 面板的坐标是负的**（`geom=-772,-687`，实测），也就是说它被布局放到了窗口之外。这是**本轮之前就存在**
    的问题（右栏四块面板的最小高度之和超过可用高度），本轮只把它测出来，没有修——修它需要重新分配右栏，那是独立的
    一项工作，重新开启条件就是「有人要读拟合结果」。

**六、图的映射现在有像素级的断言。** 屏幕上那条磁场线画得很小，看上去像 bug；把同一场景渲染进 600x200 的位图并
数像素之后，结论是**映射正确、期望错误**：fit 是**均匀**的（一个缩放同时给两个轴），在宽而扁的矩形里由高度决定，
所以内容居中、左右留白，而左右留白正是「圆不会被画成椭圆」的代价。用例现在断言的是映射本身的算术算出来的四个像素
位置（±3 px），以及左右那一百多像素的空白。这条用例第一版就抓到了自己的两个错误：先按「内容应该铺满宽度」断言，
再按“非白即内容”扫描——后者把左上角的比例标签 `8.8 R_E` 当成了内容（最左内容像素是 6 而不是 216）。现在的规则是
「与背景色的差超过阈值，且不在顶部标签带里」。

### 9.23 旗舰实验终于有了记录：一次运行 → 一条迹，以及「比值够用而质量不够」这件事

**这一项修的是一个和画面无关、却比画面更要紧的缺口：磁场套件的运行不产生任何迹。** 在此之前它的产物是报告、位置快照
与场表——**没有随时间变化的记录**，于是没有测量、没有不确定度、也没有任何可回溯的来源：平台围绕的那个闭环
（测量→记录→不确定度→报告）对它自己的旗舰实验是死的。实测证据就在窗口里：测量面板写「no readings yet」，置信度
面板写「energy drift: not measurable」。而这两句话本身是对的——`RunResult::trace` 从来没被填过。

**接口按已有的先后顺序加宽了两处。** `IGraphRun::set_run(RunId)` 与 `trace()`：前者存在的理由是账本的次序
（「绑定先于任何写入」，所以被拒绝的构建不留条目，存在的条目背后总有一次真的跑过），后者返回运行自己的记录。两者
都是**非纯虚**，默认什么都不做/返回共享的空迹——理由与 `fields()` 逐字相同：纯虚会让每一个既有实现（包括测试里的
桩）为一个它没有的能力停止编译。控制器在**构建成功之后、第一步之前**开账本条目并把 id 交给运行，然后把迹按
`positions`/`fields` 的同一条规则**拷贝**出来。

**四条通道，每一条的存在理由都不同**，而这正是「一条迹」而不是「一个诊断数字」的论证：

  - **`speed`** 是推送器自己的数值误差诊断。磁力不做功，所以速度**严格**守恒，任何变化都是积分器的。实测 600 步
    之后相对变化 **< 1e-12**（是舍入而不是截断），而这就是读者分辨「跑收敛了」与「跑飘了」所需的那个数。
  - **`mu`** 是物理：第一绝热不变量 `m v_perp²/2B` 在磁场相对回旋轨道缓变时守恒、否则不守恒，所以它的漂移量是在测
    **这次实验到底有多绝热**——一个真实的、可测量的构型性质，而不是误差。
  - **`energy`**（焦耳）与 **`radius`**（**米**）分别服务报告与分析插件；后者尤其是测量链要读的那条：窗口的测量会话
    量的是长度，所以一条以地球半径计的通道**不应该**能被它取读数，而以米计的可以。

**顺带发现：套件一直只存了「比值」，而报告需要「质量」。** 推送器每级都除以质量，所以它要的是 `q/m`，存一个比值
正好；而能量是 `m v²/2`、`mu` 是 `m v_perp²/2B`——两者都需要 `m` 单独在场。于是 `EmitterNodes::mass_of` 与
`charge_mass_of` 并排，同一张表序、同一个用例钉住「哪个物种是 2」。

**单位错了一次，而抓它的是一行算术。** 第一版给速度乘了 `c`、给半径乘了 `R_E`，于是记录出来的速度是 **8.99e14 m/s**、
半径是 **2.68e14**。定案只用了一行：L 壳 6.6 记录成 **4.2e7**，而 4.2e7 正是 6.6 个地球半径的**米数**——状态本来就是
SI，`positions()` 乘 `kNormalizedPerMetre` 是为了把它**换回来**。两个调用者现在对「状态是什么单位」这件事一致，而
分歧的成因是在一个「换算只在边界发生一次」的套件里做了第二次换算。

**`mu` 的判据是推导出来的，不是选的。** 绝热不变量在回旋半径相对场尺度不可忽略时本来就会漂：`rho/L` 由
`rho = v/omega_c`、`omega_c = (q/m)B` 给出，这个构型下是 **7.2e-3**，实测 600 步的漂移是 **1.55e-2**——约两倍，同量级。
所以用例断言的是**围绕这个预测的带**（0.5~5 倍），并另外断言速度的守恒比 `mu` 的漂移好 **九个数量级**：速度漂成那样
是积分器坏了，而 `mu` 完全不漂是诊断坏了。第一版断言 `< 1e-3`，那等于断言绝热近似是精确的——它不精确，而这个平台
不该做这种声明。

**门禁的读法又一次咬人，而且这次咬出两个陈旧的 id。** 本轮新增的用例被 C6 报成孤儿：它认领在 `run.hpp` 里，而那两处
`@tests` 写在 `///` 行上——**契约门禁只读块注释**，`///` 的 `@tests` 从来就没被收集过（core 计数里那句「10 个短体运算符
无契约注释」说的就是它们）。把同一个 id 挪进文件顶部的块注释之后，门禁**立刻**报出两处此前的谎言：一个引用了**从不
存在**的用例，另一个前缀写错（`run.` 而非 `render.`）。两者都写在 `///` 上，所以都是「写下来了」而「没有被检查」——
这正是这一节反复出现的区分。同一轮还踩了一次换行坑：用脚本把该文件读改写一遍之后，E2 报出 606 处 CRLF——Python 在
Windows 上默认把 `\n` 写成 `\r\n`，而仓库要求 LF；修法是按字节替换而不是再读改写一遍。

### 9.24 闭环接上了：一次 provider 运行 → 一条读数，以及四个链节各自缺在哪里

**上一轮让旗舰实验有了记录，这一轮把「记录」接到读数上，并且把这条链逐节钉住。** 链条是四节：provider 的运行记录、
控制器开账本条目并在第一步之前把身份交出去、**窗口把记录拷进测量会话**、用户按下测量按钮取到一条带来源的读数。
前面两节上一轮已经做过并有用例；这一轮补的是后两节——而它们此前从未被验证过，因为**在迹为空的时候它们什么也不做**：
`run_once` 里那个「按名字搬通道、按样本搬数值」的循环是对的，只是从来没有数据流过它。

**两处新用例，各自钉住自己那一节。**
`run.controller.a_provider_run_records_under_the_ledgers_identity`（model 分区）：报告里的 run id 有效、在控制器自己的
账本里查得到、与迹携带的 id **相同**、`report.samples` 等于迹的长度，通道与样本是**拷出来**的（不是借用——运行在
`run()` 返回时就销毁了）。它同时钉住一个**顺序**：`set_run` 会重建整条迹，所以「控制器先跑再命名」会交回一条空记录；
用例里那句 `REQUIRE_FALSE(ran.trace.empty())` 就是「身份先于第一个样本到达」的证据，与算子路径为账本写下的那条顺序
是同一条。
`qt.views.measurement.a_provider_run_closes_the_loop`（views_qt 分区）：用桩 provider 驱动窗口的 `run_once`，断言测
量会话里的迹**被替换**（演示种子留下的两条通道不见了，只剩运行自己的那条 `radius`）、run id 有效、样本数等于
`kSteps`，然后 `measure_selection` 取到的那条读数**等于迹的最后一个样本**且来源是被选中的那个节点。用桩而不是套件，
是因为被测的是**窗口的那一节**；需要磁层才能验证的用例，验证的是两件事。

**桩的第一版一次调用只记一个样本，用例当场抓住了它。** `IGraphRun::advance(steps, dt)` 接的是**步数**，调用者把整
次运行的步数一次交进去，所以一次调用记一个样本的实现交回的是一条**只有一个点的时间序列**——而 `size() == kSteps`
那条断言就是为此存在的。这条值得写下来，因为它不是笔误：真实运行的 `advance` 自己循环，桩必须照做，否则桩与真实
实现在**契约最容易读错的那一处**上分叉。

**`///` 上的 `@tests` 是装饰，这一点第二次咬人。** 两个新用例都被 C6 报成孤儿，而它们的 `@tests` 明明写在了对应声明
上——写在 `///` 行上，而门禁只读块注释。认领必须放进文件顶部的块注释（`editor_window.hpp` 与 `run_controller.hpp`），
两处改完立刻绿。上一轮记过一次同样的规则，这一轮是它第二次生效：**写下来**与**被检查**之间的差别，不是文风问题。

**图形化检查做到哪一步，以及没做到哪一步。** 打开 `ring.qpd`（偶极子 → 环形发射器 → Boris 推送 → 粒子渲染）按下运行：
画布上四个节点连线正常、状态栏写 `nodes 4 | edges 4 | graph v9 | runs 1`（**`runs 1` 就是账本条目**——provider 路径此
前不开条目），底部粒子面板画出八个黄点绕着一颗蓝地球，那是粒子视图第一次真的出现在屏幕上。按 Ctrl+M 时状态栏给出
**「Select the node to take a reading from」**——测量路径确实跑了，并且在没有选中节点时诚实拒绝。**没做到的是选中节
点**：合成鼠标点击始终没有落在画布的节点上，而原因我**没有查清**——截图的像素与应用接收到的逻辑坐标不是 1:1（本机
缩放），三种坐标系的换算我试了两轮仍未对准，于是停止猜测。因此「读数出现在面板表格里」这件事由上面那条 Qt 用例覆
盖，**没有**得到视觉确认；这句话写在这里而不是省略。

### 9.25 第一个标量产物：区域掩码，以及「谁该排序」这个问题

**参考实现的 `combine.py` 有五个节点（add / mul / blend / mask / resample），其中 add 已经在 qp 里，而 mul 与 mask
是一对：**`mul` 是「矢量场 × 标量场」，`mask` 是那个标量场的来源。之所以先做 mask，是因为**这个套件里有插座在等标量
场而没有任何东西能生产它**：Boris 的 `drag` 插座（`kPortDrag`，单位每秒）按端口类型接受 `kScalarField`，而
`field_nodes.cpp` 里此前每个 bake 都产出三个分量。这与电场节点是同一个形状的价值——**一个早就被声明、却没有任何生
产者的插座**。

**它是这个套件的第一个标量产物，而「标量」不是一个缺失的量纲而是一个真实的量纲。** 权重是纯数，描述符里
`component = scalar`、`dimension` 全零，一个假设「每节点三个分量」的消费者会把自己的样本读错位——它拿到的不是零
而是**别的节点的值**，而那看起来像数据。用例因此把两件事分开断言：区域判据（逐节点，不是抽样）与表的形状
（`is_vector()` 为假、`component == scalar`、样本数等于点数）。

**权重只有 0 和 1，从不插值，这是决定而不是简化。** 掩码是**区域判据**；一张中间值的表会是对一条这个节点并不建模
的边界的主张。参考实现里需要平滑过渡的那条边界是磁层顶模型，那是另一个节点，将来以另一个节点的身份到来。

**日侧/夜侧用穿过中心的终止线平面，而简化被写下来了而不是藏起来。** 参考实现把平面放在下游十个地球半径处，因为那
是**磁层顶**站立的位置；那个驻点距离是边界模型的属性，不是掩码的——等这个套件长出边界模型，它就成了那个模型的参数。

**「谁该排序」这个问题被一次失败的断言逼出了答案。** 半径对的排序写在 `read_mask` 里（用户在属性面板里把两个半径
写反了，说的还是同一个壳层，而 `MaskSpec` 的不变量就写着有序），而第一版用例却把这个断言加在 `bake_mask` 上——
于是它失败了，并且失败得正确：一个**直接构造**的反序 spec 烘出来的是一张全零的表，而全零的表与「这个区域里恰好没有
节点」无法区分。修法不是把排序搬进 bake，而是让 bake **拒绝**反序：读入端排序（用户的意思），bake 端拒绝（调用者
没有走读入端）。两处一条规则、两种动作，各自都有理由，并且各自都有断言。

### 9.9 内容的**类别**已经完成，具体内容仍需继续写（框架完成度审计）

> 判据只有一条，而且是这个仓库从第一天起就写下的那一条：**加这一类内容是否需要新接口。** 如果不需要，
> 那说明框架的那一格是空的、可用的；如果需要，那说明框架缺一个概念，那是框架的活。所以下面每一项都分成
> 「内容本身还缺什么」（可以慢慢写）与「接口还缺什么」（不能拖）。

**已完成的内容类别，以及各自新增了什么接口：**

| 目录 | 内容类别 | 为它新增的接口 |
|---|---|---|
| `plugins/mechanics` | 积分器与批算子（`IBatchAdvancer`） | 无——接口先于它存在 |
| `plugins/formats/qpjson` | 文档格式（`IDocumentFormat`） | 无 |
| `plugins/formats/csv` | 迹导出（`IExporter`） | 无 |
| `plugins/instruments` | 测量器件（`IInstrument`） | **`PluginHost::add_builtin_instrument`** |
| `plugins/analysis` | 回归与不确定度传播（无接口，纯函数） | **无，`core/` 一行未改** |
| `plugins/models` | 物理模型（`IOperatorBinder` + `NodeDesc`） | **无，`core/` 一行未改** |
| `plugins/formats/value_text` | 端口值 ↔ 文本（无接口：纯函数） | **无**（是为第二个格式做的一半准备，见下） |
| `plugins/examples` | 示例实验与闭式预期（无接口：纯函数 + 图） | **无新增接口**，但写它的过程中发现并修了 `graph/execution` 的一处缺陷 |
| `plugins/experiments` | 教师层实验包（无接口：包一层信封 + 委派） | **无，`core/` 一行未改**，而且也不需要抽取编组（见下） |
| `plugins/magnetosphere` | 地磁场与粒子（场模型节点） | **无，`core/` 一行未改**；它是 `core/graph/particles` 的第一个内容消费者 |

九类内容里只有一类新增了接口，而那一处新增**不在 `core/` 的契约层，在宿主的登记路径上**——理由是只有
`add_instrument` 时，一台器件必须来自被装载的插件，于是没有插件的构建没有任何仪器。那是「框架缺一个概念」的
教科书例子，而且形状值得记住：**它不是内容写不出来，而是某一类构建下这类内容根本不可达。** 一个只有测试夹具
能到达的能力位，看起来每一项检查都是绿的。

**本阶段：`experiments` 是第二个格式消费者，而它证明了抽取编组**不是必要的**。**
本节原先记的结论是：写第二个格式之前必须先把 `qpjson` 里那 ~450 行节点/边/参数/布局的编组抽成一层，否则就是把它抄一遍。
实际做下来，第二个格式**根本不需要自己的编组**：一个实验文件把整份 `.qpd` 作为**一个嵌套成员**携带，而 `QpJsonFormat` 解析它。

所以 `plugins/experiments` 只拥有一层信封：一个 marker、一个版本号、一个名字、一句说明，加一次委派。
它甚至不知道节点长什么样：嵌套成员是作为**文本**交给代理的，所以全仓库只有一个图 JSON 解析器，两个格式**不可能**漂移——因为会漂移的那部分只有一份实现。

**证据不是这句话，是一条用例。** `experiments.a_refusal_is_the_documents_own` 向一个 `.qpx` 里塞一张
把两条边接到同一个输入端口的图，而回来的拒绝是 **`QpJsonFormat` 自己的 `duplicate_edge`**，原样透传。
如果这个插件自己读节点，它就必须给“重复的边”自己造一句话，而两句话迟早会对“什么算重复”有不同意见。

**它被挂载在哪里，以及为什么只能在那里。** `views/app/main.cpp` 把 `.qpx` 挂载在 `.qpd` **之上**：`ExperimentFormat` 的构造函数收一个 `IDocumentFormat&`，
而不是去命名 `qpjson`，所以“实验包写在哪个文档格式上”这件事**只有应用程序能决定**，而两个插件互相不认识。
换一个二进制文档格式，实验包只需要改这一行。

而这一步曝出了一个**顺序依赖**，值得单独记下：`content_host`（组合根）原本在格式之**后**构造，而它在每个格式都自给自足时无害——一旦有一个格式需要节点目录，它就不再无害：
实验包描述每个参数时要问目录“这个输入是什么”（标签、单位、上下限），而目录是主机从目录里的插件加载出来的。
**一个建在空目录上的格式不会报错，它会把每个参数静默地描述成一个裸数字。**
于是组合根被移到格式之前，而那不是洁癖：它是“谁先存在”这件事的一部分。

**一个条件因此被改写而不是满足。** 本节原来的重新开启条件是“第二个格式的需求真的出现时，先做编组抽取”。
需求出现了，而抽取没做——因为需求本身说明了它不必要。
这是本仓库第一次“一个已记录的重新开启条件被实测推翻”，而它值得单独记下来：
**条件写的是“什么时候做”，而不是“必须这样做”，而一个把前者读成后者的人会先写 700 行抽取再发现它没用。**
同样值得记下的是它与一层之下 `value_text` 的对照：
那里抽了一块，因为两个格式需要的是**同一个计算**；这里没抽，因为一个格式可以直接**调用**另一个。
两条路径都对，区分它们的不是哲学而是实测。

**`value_text` 不是一类内容，它是「写第二个格式」那件事被拆出来的第一半。** `plugins/formats/qpjson` 里有
一千行，而大部分不是 JSON——是节点、边、**参数**、布局在两个方向上的编组。本轮把其中**参数**那一半抽了
出来：`ports::Value` ↔ `（kind 名，文本负载）`，一次实现，任何文本格式都用它。它刻意**不是一个格式**：
它决定一个参数**是什么**，格式决定一个文件**怎么拼写**——引号、缩进、转义都是格式的事。三个拒绝（现场
句柄、非法 UTF-8、非有限数）因此从「每个格式各写一遍」变成「一次」，新格式继承而不是重新推导。

抽出来的时候抓到两个实现级的错误，都记在代码里：**（1）`float` 必须按 `float` 格式化**，不能过 `double`
——`static_cast<float>(double_round_trip(x)) != x` 对某些 `x` 成立，于是「存一次再读回来」会在最后一位上
改掉一个参数，而 `ports::Value` 自己的契约（`static_cast<float>(to_double()) == as_f32()`）正是那条会被
悄悄破坏的不变式；**（2）`dim` 的「恰好七个轴」不能再用一次 `find` 判断**——消费完七个轴之后游标正停在
第七个逗号上，于是 `find(',', start)` 找到的是那个逗号本身，八个轴的负载也会被当成合法。改成记录
「最后一个被消费的位置」之后，多余的尾部就无处可藏。

剩下的一半——节点、边、布局的编组——仍然是 `experiments` 的前置条件，规模比这一半大，理由与测量都写在
上面第 2 条里。**先做参数这一半而不是先做 YAML**，是因为它是两半中与格式无关的那一半：做完之后再加格式，
需要写的只有「文本树 ↔ 这两根字符串」。

**尚未开工的内容，以及各自卡在哪：**

1. **`views_items`（渲染项）**——卡在**能力位**而不是接口：`host` 目前不授权 `render_domain` 与
   `field_domain`（见 §6.2），因为没有内容贡献它们。前置条件是「先有一个渲染域的消费者」，而渲染域的消费者
   是视图，视图又还没有第二种（§9.2）。这是本仓库唯一的**循环前置**，所以它排在最后是结构性的，不是排期
   问题——说清楚这一点，是为了让下一个人不要以为先写一个 `views_items` 插件就能把它解开。
2. **`experiments`（教师层 YAML）**——卡在**第二个格式消费者**，而且这个前置条件的**成本已经被量过一次**。
   本轮动手写了 `plugins/formats/yaml`（块式 YAML 子集 + `IDocumentFormat`），写完读写两半、还没接图之前
   停下并**整个撤掉**了：因为量出来的结论是**解析器是小的一半**。`qpjson_format.cpp` 有 1007 行，而其中大部
   分不是 JSON——是节点、边、参数、布局在**两个方向**上的编组，而 YAML 解析器会坐在同一份编组的第二份副本
   上面。也就是说真正的成本不是「写一个 YAML 解析器」，而是**先有一层共享的编组**，两个格式都用它。

   这个测量改变了前置条件的形状，值得记下来：**该做的不是第二个格式，是把 `qpjson` 里的编组抽出来。**
   抽出来之后，任何文本格式（YAML、TOML、教师层实验描述）都是一个「文本树 ↔ `Graph`+`ViewLayouts`」的薄
   适配层，而 `experiments` 就退化成内容。反过来先写 YAML，等于把那 700 行编组抄一遍，两份副本必然漂移——
   而漂移的表现是两个格式对同一张图读出不一样的图，正是 `persist` 存在的理由要防的那种。**重新开启的条件
   因此改写为：**当第二个格式的需求真的出现时，先做编组抽取那一步，它自己有回归测试（现有 `qpjson` 往返用例
   就是它的验收），然后 YAML 是几天的活而不是几周的活。

   本轮撤掉代码而不是留下未完成的模块，是同一个判断的另一半：一个编译不过、测不了的 `IDocumentFormat` 实现
   比没有更糟，因为它看上去像一个已有的能力。
3. **`examples`（示例图库）**——**已完成**。写它的过程中暴露了 `graph/execution` 的一处真缺陷，值得完整
   记下来，因为它是「内容测试框架」这句话唯一一次真的兑现：`GraphRun::prepare` 与 `check_run` **自己构造状态
   布局**（`StateView::zeroed(particles)`，分量数默认 3——力学家族的形状），而布局正是 binder 在决定能不能跑
   一个节点时拿到的东西。于是状态是 2 个分量或 4 个分量的模型会被问到一个它不接受的形状、拒绝、被报成
   「这张图没有可跑的东西」，而调用方没有办法说别的。`plugins/models` 的单摆是 2、抛体是 4，这就是它浮出来的
   方式；**它自循环写成那天就存在，因为当时全仓库唯一的算子是三分量的谐振子。**
   修法是让调用方拥有布局（`prepare` 与 `check_run` 都收一个 `StateView`），并在同一次改动里**删掉旁边的
   `particles` 参数**——两者同时存在时，只要布局报了粒子数，那个参数就不可达：同一个数在两个地方，布局静默
   取胜。症状是一条测试：`execution.loop.rejects_unusable_arguments` 断言 `particles = 0` 被拒，改完之后它
   仍然通过、但已经不可能失败——**一个无法被反驳的参数**。还有第三处：布局的 `values` 与它自称的形状不符时
   必须拒绝，因为实现会**按那两个计数重新分配**，于是调用方传进来的畸形缓冲区被悄悄丢掉、run 在一个没人要求
   的形状上成功。是 ragged 布局那条断言抓到的。
   示例本身的形式是 C++ 而不是存好的 `.qpd` 文件，理由与图标那次不同：一个手写的 JSON 在端口变化的那一刻就
   与它命名的节点类型脱节，而没有人会注意到，直到学生打开它；生成的文件需要一个生成器加一道保持同步的门禁
   （图标表的做法），而**一个示例的正确性不是逐像素比较，是物理上的一致**，那只有测试能查。所以每个示例是
   一整场实验：一个按实验室参数设好的节点、一次真的运行、一次与**独立写下的闭式解**的比较。
   `expected.hpp` 里没有任何数值方法——一个既算轨迹又算校核数的平台是在拿实现和自己比，任何物理都能通过。
4. **具体物理内容的广度**（更多模型、更多器件、二阶与多项式拟合的用例、`v²` 阻力）——不卡任何东西，
   属于按课程需求添加。

**一个必须说清楚的结论。** 内容类别的**形状**已经完整：六类内容、六条不同的进入路径、五类零接口改动。
但这不等于平台「内容齐备」——恰恰相反，具体内容是这门课的主要工作量，而本仓库现在每类只有一两个样本。
两者的区别正是这一节想守住的：**框架的完成度可以用「加一类内容要不要改 core」来衡量，内容的完成度不能**；
把后者当前者，会让「还差很多内容」被读成「框架还不成熟」，于是去改框架——那正是这个仓库已经犯过一次的错
（把 `views::TypeCatalog` 放在消费者那一层，直到内容插件无处可放才发现）。

**本阶段：`plugins/analysis` 终于有了生产消费者，而那一步把一条规则从界面里赶了出来。**在此之前，回归只能从它自己的用例里到达：
平台的差异化卖点是“测量→记录→不确定度→**报告**”，而一份没有拟合的报告就是一张需要拷进电子表格的数据表——正是这个平台要取代的工作流。
现在 `views/qt/fit_panel` 把 `FitSession` 的报告渲染成一个拟合结果：系数与它们各自的不确定度、`chi^2`、约化 `chi^2`、`R^2`，以及被排除的读数与原因。

**选择规则因此落在了 Qt-free 的一半里，而那是一个依赖决定。**`views/model` 是**无条件**构建的，而 `plugins/analysis` 只在 `QP_BUILD_PLUGINS` 下存在；把 `views_model` 链到一个插件上，
会让“不带插件的构建”配置失败，而那个构建是真的（`check_core_standalone.py` 就是为它存在的）。
于是 `fit_session.hpp` 只答“哪些读数可以进拟合”，而调用拟合的那一行在 `views/qt` 里、在 `QP_HAS_ANALYSIS_PLUGIN` 后面：
**选择是算术，调用是连接**，而两个编译器都能断言算术。

**这一步抢出来的三个缺陷，形状各不相同。**（1）**`private` 的编译定义让一条断言变成了永远通过**：
`QP_HAS_ANALYSIS_PLUGIN` 一开始是 `PRIVATE` 的，于是测试翻译进了“本构建没有拟合器”那一支，而那一支也会通过——
**一个不能失败的绿测试比没有测试更糟**，因为汇总行说“细节看过了”。修法是让定义从 `qp::views` 公开传播，
库与测试对“有没有拟合器”只能有一个答案。
（2）**一个只调“推送选择”的刷新函数把原因留在了模型里**：
`show_channels` 只调 `apply_selection` 而不渲染，而构造函数里那次 `refresh` 跑在空列表上，于是拟合面板报了一个拒绝却没有一句话——
**理由在模型里、在任何屏幕上都没有**，而模型层存在的全部意义就是它不会被四个列名和一堆空白掩盖。
（3）**`add_sample` 的默认不确定度是零，而零不是“未知”**：
测试原本写成“五个未量化的读数应该被排除为 `uncertainty_unknown`”，而实际排除的是 `uncertainty_zero`，因为默认参数使 `UncertainValue::measured(v, 0.0)` ——
**“精确”对一个计数量是真的，对一个采样信号是假的**，而两者在拟合面前是同一件事：权重是 `1/0^2`，
所以它们共用一个理由而不是两个。测试因此改写成“同一批样本，声明了不确定度就能拟合，不声明就不能”。

**上面那张表由门禁守着，而不是靠人记得改。** `tests/meta/check_content_shape.py`（ctest 里的
`meta.content_shape`）把表里的 `plugins/...` 目录名与实际目录对比，不一致就失败——**加一个插件目录而不加一行
表，门禁当场报出来**。这一条是必须的，因为「六类内容、五类零改动」这句话是全文档最有用也最容易过期的一句：
它一旦为假，散文读起来依然正确，而读它的人正在按一条过期的事实做事。反向夹具已经验证过：临时建一个带
`src/` 的 `plugins/zz_stub/` 会让它失败，删掉即通过。它**不**检查「各自新增了什么接口」那一列——那是关于某次
提交的判断，脚本去猜就是猜；目录集合是事实，事实才是脚本能拿住的东西。

## 10. 里程碑（每期的定义已完成）


> 深度规定：每一期都必须走完 §7 的 (1)→(5)，不允许"先写实现，规范后补"。
> 但也**不允许**在类型未定型时批量预写下游函数规范——那是规范剧场。

| 期 | 范围 | 完成定义（DoD） |
|---|---|---|
| **P0** | 立法 | 计划树 + 契约模板 + 测试分类 + 门禁 + 章程落地；目录骨架就位；CI 空跑通过 |
| **P1** | `core/units/` **全深度纵切** | 类型合同冻结 → 头文件契约 → 单元/性质/静态测试全绿 → 覆盖率按证明义务核对。**用这一个模块验证整套规范可用** |
| **P2** | `core/abi/` + `core/ports/` 冻结 | 布局 `static_assert` 全绿；端口类型注册 + 单位校验测试；兼容性拒绝策略测试 |
| **P3** | `core/graph/` + `exec/` | 求值性质测试；黄金回归（对齐旧工程 19 诊断点形态）；缓存失效正确性；性能基线 |
| **P4** | `core/plugin/` + `authoring/` | 契约合规套件框架就位；manifest 模糊测试；命令总线 + 撤销测试 |
| **P5** | 首个域插件包（力学：弹簧振子 / 斜面 / 碰撞） | **零核心改动证明**；四条平台承诺的自动化验收全绿 |

### P5 的验收断言（对应章程 §6）

| 承诺 | 自动化证明方式 |
|---|---|
| 加仪器不改模型 | CI 中新增一个仪器插件，diff 必须为空（除插件目录） |
| 加实验 = 写 YAML | 新实验无编译产物，直接加载 |
| 改精度 → 改不确定度 | 同一实验两组精度，最终不确定度必须不同（且方向正确） |
| 同 seed 逐位复现 | 双跑比对，逐位相等 |

> **P1 那条纵切的意义**：先用一个模块把整套规范跑通，证明这份流程本身可执行，
> 再按同一模板复制到其余模块。否则会写出一份没人能照着执行的规范——那比没有规范更糟。

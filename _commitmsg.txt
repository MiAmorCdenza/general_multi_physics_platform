chore(licence): license the project under Apache-2.0, add the Qt module licence gate

LICENSE is the canonical Apache License 2.0 text, verbatim. The project is now
explicitly reusable: anyone may use, modify and redistribute it, including in
closed-source products, with attribution and a patent grant.

Why Apache-2.0 rather than LGPL-3.0, and why it follows from the architecture
rather than from taste: the charter's central claim is that views/ and plugins/
can be deleted outright while core still builds and passes every test -- that is,
core is *designed* to be a reusable foundation. A foundation meant for reuse
should be made as easy to reuse as possible, not gated behind a judgement call.

The LGPL-3.0 objections, in order of weight:

  - core is a STATIC library linked into executables. LGPL-3.0 section 4 permits
    that only via 4(d)(0), which requires shipping object code so a recipient can
    relink. For software handed to universities that is an obligation nobody
    exercises but everybody must satisfy. Taking 4(a) instead would mean turning
    core into a DLL -- changing the packaging to satisfy a licence rather than a
    technical need.

  - LGPL is written for a Library linked by an Application; this project is both
    a framework and the finished application. Forcing that distinction onto a
    single product makes both roles true at once, and the obligations add up.

  - It draws a line through the plugin ecosystem that depends on how a plugin is
    BUILT: a DLL plugin using a defined interface is a work that uses the Library
    and stays unaffected, while a plugin that statically links core, or modifies
    it, inherits the obligations. A plugin author should not have to read licence
    law to know whether they may keep their instrument closed -- that sits badly
    with the promise that adding an instrument needs no model change.

  - copyleft works against the goal here. What the project wants from
    universities is adoption and citation, not restriction; LGPL deters exactly
    the people it wants to attract.

Compatibility confirmed in the direction that matters: Apache-2.0 code may be
combined into an LGPL-3.0 work, not the reverse. Qt is that one-way case, so
project Apache-2.0 plus Qt LGPL-3.0 linked dynamically is a clean combination.
The licence decision also strengthens the existing no-Qt-Charts rule rather than
relaxing it: the distributed binary is now more permissive than LGPL, so a
GPL-3.0-only module is even less admissible.

New gate: scripts/check_qt_modules.py, with a self-test holding 4 negative
fixtures, 2 positive ones and a skip case. It reads the generated link lines
rather than the source, because a source scan can only find an #include -- it
misses a CMake component declaration with no include in the scanned file, and it
misses a transitive pull through an LGPL module that depends on a GPL one. What
matters legally is the set of libraries that would ship, and the build system is
where that set is decided.

Running it against this project's own tree immediately found a hole: Qt names a
debug build Qt6Chartsd.lib, so comparing raw file names would let a debug build
through -- and a debug build is precisely what a developer links while
prototyping the chart they are about to ship. There is now a fixture for it.

THIRD_PARTY_NOTICES.md records every dependency and its obligations, including
what must accompany a distributed binary and what deliberately must not. LGPLv3's
full text is deliberately NOT committed: there is no Qt code in this repository,
so adding it would suggest otherwise. It belongs to the distribution package.

README.md was 32 bytes; it now states what the platform is for, the four promises,
the layer layout, how to build (including the optional Qt view layer), and the
licence terms.

# 测试与验证规范

> "每个函数都必须过单独的测试与验证"——这句话要能执行，必须拆成**八类**，
> 每类绑定不同的工具、不同的目录、不同的 CI 阶段。混在一起谈等于没谈。

---

## 1. 八类测试

| # | 类别 | 回答什么 | 工具 | 位置 | CI 阶段 |
|---|---|---|---|---|---|
| 1 | **单元** | 这个函数按契约工作吗 | Catch2 v3 | `tests/unit/` | 每次提交 |
| 2 | **静态契约** | 布局/尺寸/对齐是否如约 | `static_assert`、`offsetof` | `tests/abi/` | 每次提交 |
| 3 | **性质** | 不变量在所有输入下成立吗 | RapidCheck | `tests/property/` | 每次提交 |
| 4 | **黄金回归** | 数值结果和基准逐位一致吗 | 固定输入比对 | `tests/golden/` | 每次提交 |
| 5 | **确定性** | 同 seed 两次跑得出同一结果吗 | 双跑比对 | `tests/determinism/` | 每次提交 |
| 6 | **性能红线** | 有没有变慢 | Google Benchmark | `bench/` | 夜间 + PR（超阈值） |
| 7 | **模糊** | 畸形输入会崩吗 | libFuzzer | `tests/fuzz/` | 夜间 |
| 8 | **契约合规套件** | 任意实现都满足接口语义吗 | Catch2（可复用套件） | `tests/contract/` | 每次提交 |

**第 8 类是本项目最关键、也最容易被漏掉的一类。** 详见 §8。

## 2. 第 1 类：单元测试

- 一个函数可以有多个用例；一个用例只测**一个**契约条目。
- 用例 id 命名：`<module>.<function>.<scenario>`，与函数契约的 `@tests` 字段**逐字对应**。
- 禁止在单元测试里做 I/O、启动 Qt、加载插件——那些属于集成测试。
- 断言前置条件：违反 `@pre` 的调用必须在 debug 下触发断言（用 `REQUIRE_THROWS` 或 `death test`）。

```cpp
TEST_CASE("units.quantity.construct_from_literal", "[units]") {
    constexpr auto d = 5.0_m;          // 5 米
    STATIC_REQUIRE(decltype(d)::dim == Dim{1,0,0,0,0,0,0});
    REQUIRE(d.value() == 5.0);
}
```

## 3. 第 2 类：静态 ABI 契约

`abi/` 下的每个结构体都必须有布局断言。**这不是可选项——它是防止静默不兼容的唯一手段。**

```cpp
// tests/abi/test_field_buffer_layout.cpp
static_assert(sizeof(qp::abi::FieldBuffer) == 64, "FieldBuffer 尺寸改变 → 必须升 abi_version");
static_assert(alignof(qp::abi::FieldBuffer) == 64);
static_assert(offsetof(qp::abi::FieldBuffer, data) == 16);
static_assert(std::is_trivially_copyable_v<qp::abi::FieldBuffer>);
static_assert(qp::abi::kAbiVersion == 1);
```

改布局 → 断言先失败 → 强迫作者面对兼容性问题。**断言就是流程的执法者。**

另加一条**跨编译器/跨架构**验证：CI 上对 `FieldBuffer` 做一次序列化后按字节比对，
保证小端/大端、32/64 位下布局语义一致（或明确声明不支持）。

## 4. 第 3 类：性质测试（RapidCheck）

数值内核和代数类型必须写性质测试。理由：单元测试只能证明"你想到的例子对"。

量纲系统的性质集合（示例）：

| 性质 | 表达 |
|---|---|
| 乘法交换律 | `a*b == b*a`（量纲与数值均成立） |
| 乘法结合律 | `(a*b)*c == a*(b*c)` |
| 量纲精确性 | `(5.0_m * 3.0_s).dim == Dim{0,0,1,0,0,0,0}` |
| 单位往返 | `parse(unit_symbol<D>())` 得到的量纲 == `D` |
| 加法同维 | 不同量纲相加**必须编译失败**（`static_assert` 负向测试） |

数值内核的性质集合：

| 性质 | 表达 |
|---|---|
| 能量不增 | 无外力时总能量漂移 < 上界（**不要求守恒，要求不发散**，见 C2） |
| 二阶收敛 | 步长减半，误差降为 1/4（容差内） |
| 时间可逆 | 推进 +dt 再推进 −dt 回到起点（容差内） |
| 有限性 | 任意有限输入 → 输出必有限（钳制生效） |
| 粒子数守恒 | 无 respawn 时总数不变 |

## 5. 第 4 类：黄金回归

- 每个数值内核、每个实验模板都必须有黄金用例：**固定输入 → 固定输出的逐位对照**。
- 基准数据以二进制 + 哈希入库（不进 Git LFS 以外的工具）。
- 阈值：默认 `max|Δ| == 0.0`（逐位）。确需容差时，必须在用例里写明理由和量级。
- 参考先例：旧工程的 "19 诊断点逐位对照（max|Δ|=0.00）" 就是本类测试的正确形态。

断言里必须打印**全部**诊断点，而不是在第一个失败点停住——
这样一次失败就能看到漂移的形状（是整体偏移还是单点爆炸）。

### 5.1 浮点断言的铁律（P1 实测教训，必读）

`STATIC_REQUIRE` 与 `REQUIRE` 在浮点上**不等价**，用错会产生假通过或假失败。

**根因**：本机 MinGW 是 **32 位**目标（`i686-w64-mingw32`），因此
`FLT_EVAL_METHOD == 2` —— 浮点表达式按 **x87 80 位扩展精度**求值。
`static_assert` 里的算术在 80 位下算，运行期 `.value()` 是 64 位结果，
两者最后几位**合法地**不同。

**实测反例**（`pow<-2>(10.0)` 与字面量 `0.01` 在运行期同为 `0x3f847ae147ae147b`）：

```cpp
REQUIRE(pow<-2>(Length{10.0}).value() == 0.01);          // ✅ 通过
STATIC_REQUIRE(pow<-2>(Length{10.0}).value() == 0.01);   // ❌ 失败
```

**规则**：

| 断言对象 | 写法 |
|---|---|
| 整数、类型、`sizeof`、`offsetof` | `STATIC_REQUIRE` |
| **精确可表示**的浮点值（0.25、9.0、10000.0、-1.0） | `STATIC_REQUIRE` 可用 |
| 其余浮点值 | **必须** `REQUIRE` |
| 跨算法一致性（平方求幂 vs 连乘） | `REQUIRE` + **ULP 容差**，禁止要求逐位相等 |
| 确定性（同输入同输出） | `REQUIRE` + 逐位相等（这才是可要求的性质） |

另有一条 C++ 语法陷阱：**模板实参里的逗号会被宏当作参数分隔符**。
`STATIC_REQUIRE(std::is_same_v<A, B>)` 会解析错乱，必须用类型别名或加括号：

```cpp
using Ab = decltype(Length{1.0} * Mass{1.0});
using Ba = decltype(Mass{1.0} * Length{1.0});
STATIC_REQUIRE(std::is_same_v<Ab, Ba>);   // ✅ 清晰且不会踩宏的坑
```

**工具链前提必须被断言**：`tests/unit/units/test_floating_point_env.cpp`
把 `FLT_EVAL_METHOD`、`sizeof(long double)`、`digits` 写成断言。
换 64 位工具链时它会失败，提醒维护者重新审视所有浮点断言——这是刻意的摩擦。

**推论（写数值内核时的重要后果）**：
在 `FLT_EVAL_METHOD == 2` 的 32 位工具链上，**浮点结果依赖求值顺序与优化级别**。
因此"逐位复现"（章程 R2）必须以**固定工具链 + 固定优化级别**为前提，
运行身份必须记录这两项，否则复现承诺无法成立。

### 5.2 浮点转文本：`%.17g` 不足以保证"不同值不同文本"

缓存键、黄金基准、内容寻址都要求"值 → 文本"这一步**可区分**。
`%.17g` 只保证"文本能被解析回同一个值"，**不保证反向**。

实测（`core/graph/eval`）：

```
0.1 + 0.2  →  double 0x3FD3333333333334
0.3        →  double 0x3FD3333333333333     （两者不相等）

%.17g  →  两者都是 "0.3"        ❌ 无法区分
%a     →  0x1.3333333333334p-2 与 0x1.3333333333333p-2  ✅
```

若用 `%.17g` 做缓存键的精确比较，会把**两个不同的计算当成同一次**——
这类缺陷不崩溃，只是算出别人的结果。

**但 `%a` 的输出是平台相关的**：GCC 给最短形式 `0x1.8p+0`，
MSVC 给补零形式 `0x1.8000000000000p+0`。因此必须**归一化**
（去掉尾数小数部分的尾随零，小数全零时连小数点一起去掉）。
归一化后两个编译器给出**逐字节相同**的文本，缓存因而可跨编译器互换。

**另一条测试陷阱**：在本机的 32 位工具链下，`0.1 + 0.2` 会被编译器
**在扩展精度下常量折叠**，于是"恰好"等于 `0.3`，掩盖上面这个问题。
要测出真实行为必须用 `volatile` 强制运行期求值：

```cpp
volatile double a = 0.1, b = 0.2;
REQUIRE(a + b != 0.3);          // ✅ 真实行为
REQUIRE(0.1 + 0.2 != 0.3);      // ❌ 常量折叠后相等
```

## 6. 第 5 类：确定性

对应章程 R2。每个带随机性的模块都要有：

```cpp
TEST_CASE("determinism.same_seed_identical_readings", "[determinism]") {
    auto run_a = run_experiment(cfg, /*seed=*/12345);
    auto run_b = run_experiment(cfg, /*seed=*/12345);
    REQUIRE(run_a.readings() == run_b.readings());   // 逐位，不是近似
}
```

另外必须有**反向**测试：不同 seed **必须**产生不同结果。
否则一个"永远返回常数"的退化实现也能通过正向测试。

## 7. 第 6、7 类：性能与模糊

### 性能红线（来自旧工程的 §8 性能红线）

| 场景 | 门槛 |
|---|---|
| 粒子推进 | 2 万粒子 × 5 步/帧 × 60fps，**每帧零 Python 调用** |
| 场传输 | float32 单张 ≈ 19MB，不得出现整张 memcpy |
| 场缓存 | ≈ 200MB 上界，超出必须淘汰而非增长 |

规则：**基线一旦确定，只允许变快，变慢超过 5% 即 PR 失败**（除非附 ADR 说明）。

### 模糊测试

| 目标 | 不变量 |
|---|---|
| 插件 manifest 解析器 | 任意字节输入不得崩溃；拒绝畸形输入而非 UB |
| 图 JSON 加载器 | 任意字节输入不得崩溃；拒绝有环图 |
| YAML 实验描述加载器 | 同上 |
| 表达式解析器（若引入） | 不得逃逸沙箱 |

## 8. 第 8 类：契约合规套件（最关键）

> **对每个插件接口，写一套测试；任何实现都必须通过这套测试。**

这是"边界能被规模化守住"的唯一方式。否则每接一个新插件都要重新 code review。

### 形态

```cpp
// tests/contract/ode_kernel_contract.hpp
// 任何 ode.explicit 内核实现（Boris / 蛙跳 / RK4 / Verlet）都必须通过本套件。
template<class KernelImpl>
void run_ode_kernel_contract() {
    SECTION("二阶收敛") { ... }
    SECTION("能量漂移有界") { ... }
    SECTION("时间可逆") { ... }
    SECTION("非有限值被钳制") { ... }
    SECTION("无分配（计数分配器）") { ... }
    SECTION("输入缓冲区不被修改") { ... }
}
```

### 各插件接口对应的合规套件（必须与接口同时提交）

| 接口 | 合规套件必须验证 |
|---|---|
| `ISimModel`（仿真模型） | 纯函数性、时间可逆性（若声明）、量纲正确、无全局状态 |
| `IInstrument`（仪器） | 只产出读数不产出真值（R1）、误差模型随精度变化（承诺 3）、可重复 |
| `IKernel`（数值内核） | 收敛阶、稳定性、无分配、确定性 |
| `IView`（视图） | 不得订阅真值层（R1）、崩溃不影响内核、布局状态自持 |
| `ITransport`（传输适配器） | 无损往返、版本协商、拒绝不兼容版本 |
| `IAnalysis`（分析/拟合） | 输入输出类型正确、异常输入不崩、结果可追溯至数据集 |

### 门禁规则

> **新增插件接口时，必须同时提交其契约合规套件，否则拒绝合并。**

这条把"边界"从文档变成了可执行物。

## 10. 覆盖率与"证明义务"

覆盖率**不是**目标，**证明义务**才是目标。

| 对象 | 证明义务 |
|---|---|
| 契约的每一条 `@post` | 必须有一个测试**专门**验证它 |
| 契约的每一个错误码 | 必须被至少触发一次 |
| 每个 ABI 结构体 | 必须有布局 `static_assert` |
| 每个插件接口 | 必须有合规套件 |
| 每个数值内核 | 必须有黄金回归 + 性能基线 |
| 每个随机模块 | 必须有确定性双跑测试 |

> 覆盖率数字仅作为**发现未测试代码的探针**使用，不作为验收标准。
> 一条被覆盖但没断言任何东西的测试，等于没测。
